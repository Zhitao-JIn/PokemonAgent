你在处理一局刚刚结束的游戏记录。这是**两件事的合并**，按顺序做，不要跳步：

1. 先审查每一条 step 记录的可靠性——它是模型自己当时的说法（"当时看到 →
   按了什么 → 之后变成"），可能记错。
2. 再把**可信的那些**蒸馏成一条跨局摘要经验。**不可信的记录不能被当成
   真实发生的操作写进摘要**——它的自述本来就没通过核对，把它当经验记下来，
   等于把可能是错的东西固化成"教训"，会在别的局里被检索回来照着用。

这两步分开判断、但只用一次输出给出结论。

## 第一步：判定规则（逐条给出 reliable / why）

对每一条记录，对比「做了什么」和「之后变成」的两份快照（位置、朝向、场景、
覆盖层、对话框、地图编号），判断是否合理一致：

**方法论层（不依赖具体场景，任何时候都能判）**：
- **前后状态完全相同、但动作声称"做了某事并有效"**——可疑（什么都没变，
  哪来的效果）。
- **声称达成的效果和实际快照对不上**（比如声称"逃跑成功"但画面还在同一场
  战斗里、声称"打开了菜单"但画面没有任何变化）——可疑。
- 单纯"按下去画面没变"不必然可疑——可能是被挡、被拒绝、或这个场景下本来
  就该没反应；这类判断需要知道"在这个场景/这个动作下，没反应算不算正常"，
  属于领域层，不要凭感觉判。

**领域层（要靠下面「检索到的相关领域知识」判断，不知道就别凭训练时的印象猜）**：
- 下面的知识提到了这条记录涉及的场景/动作该有什么效果时，对照它判断记录
  是否合理；
- **下面没有检索到能覆盖这条记录场景的知识时，不要凭常识硬判**——按
  `reliable: false` 处理，`why` 写"无相关领域知识，无法确认"。宁可让这条
  记忆在这一步被少喂一条，也不要把没有依据的猜测当成验证过的结论。

## 第二步：只用可信的记录写跨局摘要

**判完第一步之后**，只拿 `reliable: true` 的那些记录当"这一局真实发生过的
事"，蒸馏成一条跨局摘要（其余人看不到这些记录本身，只会看到你写的摘要——
把不可信的东西写进去，等于替它作了伪证）。`reliable: false` 的记录不要在
`summary`/`reusable_patterns`/`critical_decisions` 里当成事实引用；如果它
本身就是这一局的一个失败信号（比如"自称按键有效、实际前后画面没变"这种
矛盾本身就值得记），可以体现在 `failure_points` 或 `quality_rationale` 里，
但要说清楚"这一条的自述没有通过核对"，不能写成"这一步做了 X"。

你是一个资深宝可梦玩家，负责从这一整局游戏经历中蒸馏出可复用的经验。
产出的是一条**跨局摘要记忆**：以后在别的局里，遇到相似场景时会被检索回来。

## 生成要求
1. 用简明扼要的总结描述整个 episode（只依据 reliable 的记录）
2. 提取可重复利用的游戏策略和经验模式
3. 指出关键决策点和潜在失败环节
4. 评估记忆质量(0.0-1.0)和适用场景——如果可信记录很少或质量参差，评分要
   相应压低，`quality_rationale` 里说明原因
5. 为记忆添加有意义的标签
6. 生成一个简短、稳定、适合文件系统的英文文件名（不要包含路径和扩展名）
7. 生成一份可直接保存的 Markdown 正文

## 输出格式

只输出一个 JSON 对象，不要有其他文字。`verdicts` 与下面的记录条数等长，
`summary` 是蒸馏出的摘要：

```json
{
  "verdicts": [
    {"index": 0, "reliable": true, "why": "up 后位置从 (5,4) 到 (5,3)，一致"},
    {"index": 1, "reliable": false, "why": "声称逃跑，但知识里这个动作对应的分支和记录里选的不是同一个，效果对不上"}
  ],
  "summary": {
    "summary": "在初心镇宝可梦中心门口反复横跳了 6 步才找到门，问题出在把 landmarks 当成了这一帧的实时位置",
    "reusable_patterns": ["站在 D 格上判断门朝哪边开，要看 known_objects 里门的坐标而不是猜画面朝向"],
    "critical_decisions": ["第 12 步：没有直接走进已确认的 D 格，而是先绕了一圈找宝可梦中心招牌，浪费了 6 步"],
    "failure_points": ["把检索到的跨地图知识当成了这一帧已经到达的证据，导致提前判断「已经到中心了」"],
    "quality_score": 0.7,
    "quality_rationale": "这局的教训具体、可复用，但样本只有一次，尚未在别的地图验证过",
    "applicable_scenes": ["interaction:door", "interaction:pokemon_center"],
    "tags": ["door", "pokemon_center", "navigation"],
    "filename": "door_navigation_pokemon_center",
    "markdown": "# 宝可梦中心门口导航\n\n站在 D 格上时，先核对 known_objects 里门的坐标，不要凭画面观感猜方向。"
  }
}
```

注意:
- `index`：对应记录序号（从 0 开始）；`reliable`: false 表示这条记录不可信；
  `why`：一句话依据，不可靠时写清矛盾在哪，或写清缺哪类领域知识。
- `summary.quality_score` 必须是0.0-1.0之间的浮点数
- `summary.filename` 只能包含小写英文字母、数字、下划线和连字符，不要包含路径或 `.md`
- `summary.markdown` 必须是完整的 Markdown 记忆正文，不能包含 JSON 代码围栏
- `summary.applicable_scenes` 只能使用以下稳定标签：`*`、`map:<数字>`、`scene:field`、`scene:indoor`、`scene:battle`、`scene:menu`、`scene:shop`、`overlay:dialog`、`overlay:choice`、`terrain:grass`、`interaction:npc`、`interaction:door`、`interaction:shop`、`interaction:pokemon_center`
- `summary.applicable_scenes` 只填写这条经验实际适用的标签；通用经验使用 `*`，不要写自然语言长句
- 两个部分（`verdicts`、`summary`）都必须提供，`summary` 内所有字段都必须提供，不能省略

## 除了文字，你还会看到截图

多帧截图已拼成**一张 3 列网格图**：帧间黑线分隔，行优先、从左到右从上到下，
按时间先后排列——时间上相邻的两帧在网格里也相邻，某格与其右侧一格之间的
画面差异就是一次按键的结果；网格有几行看图即知，最后一行不满的空格是黑色。
只附一张图时，它就是本局最后一步结束后的画面。

**截图是用来核对第一步的，不是用来重新分析的。** 每条记录里的位置、场景、
覆盖层这些字段都已经是抽好的结构化结果——**不要拿截图自己重新推算位置或
坐标**。截图真正该用来做的事，是核对**文字有没有抽错**：声称的效果（比如
"招式打出去了""买东西买成了"）在截图上是不是真的能看到对应的文字或画面
变化，而不是记录自己编的。截图和文字描述对不上时，以截图上实际看到的为准。
