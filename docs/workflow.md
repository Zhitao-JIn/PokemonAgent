# 协作流程规范（设计侧 / 执行方 / 用户）

本文是 Pokemon_Agent 的多 AI 协作约定。放在仓库 `docs/workflow.md`。

## 1. 角色与权限

| 角色 | 负责 | 不做 |
|---|---|---|
| 设计侧（Claude） | 调研、写 intent/spec/plan、派发任务、验收、裁决、**统一提交**、跟踪状态、分配 changelog 编号 | 不改生产代码（用户明说才改，并注明未跑测试） |
| 执行方（其他 AI） | 改代码、写测试、跑命令、汇报 | **不提交**：不运行 `git add` / `git commit` / `git merge` / `git rebase` / `git reset` / `git stash` / `git checkout`（切分支）。只用 `git status`、`git diff`、`git log` 等只读命令 |
| 用户 | 确认费用、本机跑真实模型、产品取舍、**合入主线** | — |

## 2. 文档

流程：intent → spec → plan → 执行 → 验收 → 合入。文档放 `docs/<主题>/`，同主题互相指向。

- **intent**：意图、依据、做/不做、待确认问题、风险、成功标准。只保留最终版，不写修订历史。
- **spec**：决定表、检查点清单、文件改动清单、测试清单、验证方式、停止条件、非目标。可标版本与修订原因。
- **plan**：步骤顺序与依赖、每个检查点的验收核对点、任务允许改动的文件、changelog 编号台账、回退方式、遗留清单。
- 交接消息不入库，每次自包含、完整重发。
- 文档由设计侧写，并由设计侧作为分支的第一个提交落库。

## 3. 任务生命周期

1. 设计侧写文档，定检查点，分配 changelog 编号，核对与其他任务有无文件交集。
2. 建分支与 worktree（见第 6 节）。
3. 发交接消息；执行方在 worktree 里做到**第一个检查点**，不提交，停下汇报。
4. 设计侧验收：读 diff、核证据、核 changelog 条目；通过则**由设计侧提交**，并放行下一个检查点。
5. 全部检查点完成后，由用户（或用户授权后）合入。

小任务只设一个检查点。

## 4. 检查点与回退

- 一次验收对应一个提交，即一个检查点一个提交。
- spec 里的每一步按“可单独验收、可单独回退”来拆。
- 回退一律用 `git revert`，不重写历史，不 amend，不 force push。

## 5. changelog

- 编号在**派发时**由设计侧分配，写进交接消息，并记入 plan 的编号台账。取号方式见第 12 节：取共享台账脚本给出的“下一个可用编号”，先登记再发消息。
- 执行方在自己的 worktree 里按给定编号写条目，不自行取号。
- 条目里的数字（用例数、pytest 尾行等）只能写亲眼见到的实数。
- 任务驳回或作废的编号留空，不回收。
- 验收时核对条目与实际改动相符，再随该检查点提交。
- 合并时 `CHANGELOG.md` 顶部插入处会产生文本冲突：在集成分支里保留两边条目，按编号排序，用单独的整理提交解决，不改编号。

## 6. 分支与 worktree

- 每个任务一条分支、一个 worktree，基于用户指定的基线提交。
- worktree 放仓库内 `.worktrees/<主题>/`，并把 `.worktrees/` 写入 `.git/info/exclude`。
- 必须在 `pyproject.toml` 的 `[tool.ruff]` `extend-exclude` 里加 `.worktrees`，否则主工作区的 `ruff check` 会扫进各 worktree。pytest 不用改：`testpaths` 只有 `tests`，且默认不进入点号开头的目录。
- 依赖不重装：用主仓库 `.venv` 的解释器（Windows 下形如 `<主仓库>\.venv\Scripts\python.exe`）直接运行。在 worktree 里禁止 `uv run`、`uv sync`、`pip install`。
- 首步验证：`python -c "import sys; sys.path[:0]=['.','tests']; import pokemon_agent; print(pokemon_agent.__file__)"`，路径必须落在该 worktree 之下，否则立即停下汇报。
- 未跟踪但必需的文件（ROM、`.env`、存档、模型缓存）不会随 worktree 带过来，由设计侧在交接里写明复制清单。
- pytest 的 `--basetemp` 放在该 worktree 内，每次换新目录。
- 用完的 worktree 由用户决定何时删除。

## 7. 冲突处理

- **预防**：plan 里列出每个任务允许改动的文件；派发前核对交集。有交集就写明合并顺序，或改为串行。
- **共享文件**（`CHANGELOG.md`、`AGENTS.md`、`CLAUDE.md`）：只在集成分支里处理冲突。
- **合并方式**：建集成分支，按依赖顺序逐个合入，合完跑一次全量 pytest 与 ruff，作为最终全绿依据。同步主线用 merge，不用 rebase。
- **分级**：只涉及文档或 changelog 的冲突按上面的规则解决；涉及生产代码的冲突，操作者停下汇报，由设计侧读两边 diff 后裁决。

## 8. 提交规则（设计侧执行）

- 提交前三项全绿：全量 pytest、`ruff check`、`ruff format --check`。无测试例外。
- 用显式路径 `git add`，不用 `git add -A`，不用 `git commit -a`。
- 提交前 `git diff --cached --stat` 确认恰好是预期文件。工作区是 CRLF、HEAD 是 LF，任何文件出现远超预期的增删行数就是行尾被整体改写，先修正再提交。用 `git diff --ignore-cr-at-eol` 核对。
- 别的任务留下的未提交改动不碰、不清理、不提交。
- 设计侧在目标 worktree 里没有可用的命令行工具时，给出完整命令，由用户执行；提交的内容与信息仍由设计侧确定。

## 9. 停止条件（执行方遇到即停，不重试、不绕过）

- 改动超出 plan 列出的允许文件范围。
- 关键哈希或 HEAD 与交接消息不一致。
- 起点全量 pytest 或 ruff 不是全绿。
- 任何真实模型调用（除非交接消息明确授权这一次）。
- 需要执行被禁止的 git 命令才能继续。
- 首步解释器验证失败。

## 10. 汇报格式（执行方）

- 改动文件清单与 `git diff --stat`。
- pytest、ruff 尾行。
- 与指示有出入处（没有写“无”）。
- 有运行结果时附结果目录路径。
- 完成检查点后停下，不自行进入下一个。

## 11. 验收结论

只有三种：通过（给出下一步）、通过但有留意点、不通过（说明具体差在哪）。通过后设计侧提交，并立即发出下一条可转发的交接消息。

## 12. 并行任务的共享台账

多个规划会话并行时，各自的会话文档互相看不见。共享状态放在主工作区根目录 `.coordination/`，**不入 git**（`.git/info/exclude` 已排除）：

- `ledger.md`：编号、活跃任务、契约触点、待裁决四张表。所有规划会话读写同一份。
- `overlap.py`：只读脚本，直接从 git 算出每个活跃分支改了哪些文件、落后主线多少个提交、落后部分碰没碰本分支的文件、两两文件交集，以及下一个可用的 changelog 编号。

规则：
1. 规划会话开工先读 `ledger.md`，再读自己的会话文档。
2. 写 plan、派发前、验收前各跑一次 `python .coordination/overlap.py`（无 worktree 的暂缓分支用 `--branch` 补上）。
3. 取号用脚本末行的“下一个可用编号”，先写进台账“编号”表，再发交接消息。
4. 派发前对着“契约触点”表自检：自己的 spec 有没有改别人已声明的契约；改了就登记，冲突写进“待裁决”，由用户裁，规划器之间不互相定。
5. 主线新增的提交碰到某活跃分支的文件时，由该分支的规划会话在下一次验收时 merge 主线进分支（不 rebase），并在台账里记一笔；没碰到不用动。
6. 任务合入或作废时销账；作废的编号标“空号”，不回收。
7. 脚本只查文件交集，查不到“同一契约两种说法”这类语义冲突，那部分只靠第 4 条的人工登记。
