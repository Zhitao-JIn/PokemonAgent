## 二、遇到的问题清单

### P1 —— 会影响「是否启动成功」判断的问题

**1. 后端启动慢（约 8–15 秒），过早探测会误判为启动失败**
- 现象：启动后 8 秒探测 `:8000/health` 无响应、无监听；约 10+ 秒后才就绪。
- 原因：uvicorn 应用启动前要 import pygame / pysdl2-dll，初始化耗时明显（err log 首行即有 SDL2 加载警告）。
- 影响：脚本本身无问题，但任何「起完就立刻探活」的自动化都会误报失败。
- 建议：探活前加就绪等待（轮询 health 直到 200，超时 30s），不要固定 sleep 几秒。

**2. uvicorn 启动日志全部写 stderr，`dev-api.log` 恒为 0 字节**
- 现象：`dev-api.log` 空；`dev-api.err.log` 里有全部 INFO（`Started server process [44660]` / `Uvicorn running on http://127.0.0.1:8000`）。
- 原因：uvicorn 默认把 logging 输出到 stderr，stdout 只留业务 print（本项目 print 甚少）。
- 影响：看错文件会误判「后端没输出 = 没启动」。
- 建议：排查后端状态时以 `dev-api.err.log` 为准；或者脚本里给 uvicorn 配 `--log-config` 统一重定向。

### P2 —— 脚本 / 配置层面的兼容性问题

**3. dev.ps1 中文输出在非交互/重定向场景下乱码**
- 现象：`Write-Host "后端 / 前端 / 日志 / 退出"` 捕获后显示为 `鍚庣 / 鍓嶇 / 鏃ュ織 / 閫€鍑?`。
- 原因：PowerShell 5.1 中 `Write-Host` 输出被管道/重定向捕获时，按系统 ANSI 代码页（GBK/936）编码字符串；脚本第 9 行的 `$OutputEncoding = [Console]::OutputEncoding = UTF8` 只影响与控制台/native 命令的交互编码，覆盖不到 Write-Host 的捕获输出。
- 影响：仅日志可读性受损，功能无影响；用户交互终端里正常（直接跑 `.\dev.ps1` 不乱码）。
- 建议（可选）：如要兼顾重定向场景，改用 `[Console]::WriteLine()` 或给 Write-Host 显式转 UTF-8 字节流。

**4. `/api/health` 不在 vite 代理白名单，会拿到 SPA fallback 而非 JSON**
- 现象：`curl http://localhost:5173/api/health` 返回 index.html（HTTP 200），而 `:5173/health` 正常代理转发。
- 原因：`web/vite.config.ts` 只代理 `/health`、`/runs` 两条前缀，`/api/*` 未配置 → vite 按 SPA fallback 返回首页。
- 影响：当前 `web/src/api.ts` 用的是相对路径（`/health`、`/runs`），未踩坑；但任何新增 `/api/*` 前缀的调用都会静默拿到 HTML，且浏览器端不报错。
- 建议：前端 API 前缀约定（`/api/*` or 裸路径）与 vite 代理白名单保持同步，别引入第三种前缀。

### P3 —— 本工作台环境观察（非项目问题，仅记录）

**5. 后台任务运行期间，PowerShell 工具新调用无输出**：后台 PowerShell 任务持有控制台/管道后，同环境内的新 PowerShell 调用返回空（exit 0 但无 stdout）。验证改走 Bash/curl 即可。

**6. Bash 管道过滤含 "powershell" 字样的 tasklist 命令被安全策略拦截**（提示 "Invoking PowerShell from Bash"），换措辞（去掉该词）或直接用 PowerShell 工具绕过。

**7. `UserWarning: Using SDL2 binaries from pysdl2-dll 2.32.10`**：无害；说明 pygame 用的是 pysdl2-dll 打包的 SDL2 二进制，而非系统安装的 SDL2。仅需知悉，无需处理。

## 三、诊断复盘（防再犯）

本次曾一度误判「后端未启动」，三重因素叠加：
1. 启动后 8 秒探测太早（问题 1）；
2. `tasklist | head -50` 截断，python.exe 排在列表后面看不到；
3. PowerShell 工具无输出（问题 5）。

最终靠 **curl health + PID 对照**（err log 中 `Started server process [44660]` ↔ tasklist 的 `python.exe 44660`）确认后端存活。
**经验：判断服务是否就绪，以 curl/实际请求为准，不要信进程列表快照和固定 sleep。**
