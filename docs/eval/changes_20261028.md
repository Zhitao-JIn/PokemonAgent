# 2026-10-28 至 10-29：为什么一天内改了这么多评测资产

> 记录人：设计侧会话。读者：之后接手评测的人（包括自己）。对应 CHANGELOG 编号见括号。一句话原因：**评测要从"一个能跑的短期集合"升级成"三档、可复现、能区分被测对象"的体系，过程中不断暴露出旧假设与旧机制的问题，每发现一个就修一个，所以改动集中。**

## 一、先说清楚的几个原则（这些决定了改什么）

1. **分层与冻结是两条轴**（`docs/eval/tiers.md`）：分层说明任务是什么性质（短期边界对齐脚本、中期边界由规划器给、长期开放有干扰），冻结只是评测手段（冻结 task 表、episode 目标表、记忆种子）。此前代码把冻结绑在 `tier` 字段上，是已知的建模债。
2. **真值只来自我们自己写的机械判据**，规划器给出的起止条件只用于评测，不参与运行控制、不决定通过与否。
3. **不靠"中途藏起本来看得见的东西"制造需要**：长期任务需要记忆，必须是因为游戏状态里本来就没有、只在上一个 run 里探索过才知道的信息；知识库的差异是数据集的设置，不是运行中途的开关。
4. **不做真正的恢复**：harness 只在启动时按 `.state` 恢复世界；memory 只是指向一个新的记忆仓库（评测里是起服务前复制种子目录）。
5. **每一步都要能复现、能核对**：起点存档由构建脚本生成并校验哈希，数据集带 `revision.json`，数字只写亲眼读到的。

## 三、数据与设计上的关键决定（及其原因）

- **M1 从"包裹送达"改为"从常青市走到真新镇并进研究所"**：原起点 `D74E=0x03`，包裹那一幕早已过去，进店不触发托付；包裹的托付对话也没说研究所在哪，记忆里本来就没有收件人的位置，所以它不能作为单独任务。路线放进知识库（`map_connections`）。
- **长期任务改为开放探索**：开局卧室，目标"离开真新镇"，游戏自带门禁（不拿宝可梦，大木会拦路）；终点分四层，干扰类型逐层叠加。第三层先建。
- **M4 的 oracle 必须自适应**：移动顾客的位置取决于时间线（加载时在 `(5,7)`，走几步后可能在 `(5,6)`），写死坐标的 oracle 在新判稳下失败；对 agent 无影响，它每步都看得到。
- **预算只在 oracle 数据上定到 3×取整，复核后保持不变**：新等待下 M2 79、M3 56、M4 104、M5 75 步，M1 因遇敌减少而显著变化，但 M1 的预算不按最短路径压低（agent 要探索）。
- **M3 的抓捕受随机数影响**：游戏随机数每帧滚动，成败取决于投球时刻；同一空转帧数重复结果相同，不是独立样本；判据只看结果，通过率看 `pass_at_k`。

## 五、这些改动对评测意味着什么

- 评测资产（数据集、判据、起点、知识、工具）现在有明确的来源与复现办法，每份都能核对哈希。
- 旧数据（`evals/dataset` 下旧格式冻结数据与 72 个 `D33` 跳过测试）没有动，等用新框架重新生成。
- 在 706 做完之前，只有短期集合可以直接评测。
