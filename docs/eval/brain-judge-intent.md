# intent —— `brain_judge` 扩容：任务完成判定的独立评测

**状态：方向已确认；进入 spec 与执行计划。**

## 一、一句话意图

把 `brain_judge` 从四条契约示例扩成一批可独立核对的真实 task 判定现场，衡量生产判定器在目标完成与未完成时的判断表现。

## 二、为什么做

`docs/spec/evals/SPEC.md` §88–89 记载，当前评测只有四条示例。它们只证明入口和四格计数能运行，无法说明生产判定器在真实任务历史上的表现，也不足以观察误判集中在哪些情形。

刚完成的 `brain_choose` 评测为单步动作选择提供了独立量尺。下一项接着检查任务层的完成判定，能把“选了什么动作”和“是否认为目标已经完成”分开观察。当前主线的 `brain_judge` 入口和四格 scorer 已存在，可沿用现有评测任务的形态。

此前采集整理中，有 190 条历史记录的 choose 请求可还原出与生产 task judge 调用完全一致的 prompt 和图片输入。它们是候选来源，不等同于 190 条已确认的 judge 评测样本：需逐条确认目标真值能依据当时的完整历史、观测和世界事实独立判定；不能用模型答复、理由或之后执行结果充当标签。该批次无法证明采集全过程的代码版本恒定，版本限制必须随数据说明。

## 三、做什么、不做什么

**做：**

- 扩充现有 `brain_judge`，测 task 层 `done` 是否与独立确定的目标完成事实一致。
- 以生产 `FromHarnessToBrainToolJudgeReq` 为输入，尽可能复用真实调用时的完整 task 历史与图片素材。
- 保留可追溯的来源和逐条标签依据；证据不足或真值有歧义的样本不进入冻结集。
- 先做只读数据可行性盘点，再由 spec 确定可冻结规模和各类覆盖。

**不做：**

- 不评测 `interrupted` 字段；本次只扩充现有 `achieved` / `done` 完成判定口径。
- 不把文档中旧 `brain_step_verify` 的“单步是否生效”混作当前 judge 契约。
- 不改生产代码、judge prompt 或判定逻辑，不以模型答案生成或修订真值。
- 不在实现与数据冻结前调用真实模型；真实模型评测须另行明确授权。

## 四、核心约定

- 标签针对 judge 请求发生时刻的目标状态，不针对整个 run 最终是否成功。
- 真值来自该时刻可见的完整历史、观测和独立世界证据。单靠模型说“完成”或“未完成”不构成真值。
- 请求还原必须与生产 task 层装配口径一致；如果候选记录不能无损还原，则保留为不适用，不拼造字段。
- 当前可用候选量、可独立判定比例和场景分布以数据盘点实测为准，不沿用旧文档里未经核实的样本配额。

## 五、成功的样子

- 冻结样本可由现有生产 judge 入口直接重放，标签来源和判定依据能逐条审阅。
- 汇总能反映完成判定的命中与两类误判，并能按经确认的样本类别查看结果及分母。
- 运行报告披露未计分的基础设施失败、数据覆盖缺口和采集版本限制。

## 六、方向裁定

用户已确认继续设计 `brain_judge` 扩容。190 条已匹配记录只作为候选；执行先审计全部 257 次 task judge 调用，再分别统计请求可还原数、真值可判数与最终覆盖。不得将 190 直接视为冻结样本数。

## 七、影响面与风险

- 预期只涉及评测数据、评测代码、测试和对应评测文档；不动 `pokemon_agent/` 生产代码。
- 最大风险是真值判定的可复核性：采集记录可精确复现模型输入，不代表目标事实必然能从现存证据独立判定。
- 复用的候选记录来自代码版本连续性不完全可证明的采集批次；若不能接受这一限制，需另行采集并获得单独的模型运行授权。
- 当前主工作区有其他任务的未提交修改。后续执行应继续在独立 worktree 中进行，不得覆盖或清理主工作区内容。
