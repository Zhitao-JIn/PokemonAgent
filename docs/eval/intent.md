## 一、一句话意图

**任何时候，一条命令就能回答"这个 agent 现在有多好、比上一个版本好还是差、差在哪、花了多少"——
而且这个答案不依赖任何一个模型的自我评价。**

## 二、为什么现在做

1. **现在的成功率是模型说了算。** `Termination.GOAL_DONE` 是 `success` 的唯一来源，由 judge 模型给出；
   `docs/experiments/0827-knowledge-baseline.md` 机械复核 124 次 run：judge 记 115 次成功，实际 102 次（假阳 16、假阴 3）。
   当时的复核脚本已不在仓库。
2. **没有批次入口，也没有报表。** ROADMAP F1 📋；原 `evaluation/` 已整体删除（`docs/spec/README.md` 第四节）。
   `experiment/real_check/` 核的是"链路对不对"，明确"不能证格读到的 state 值"，更不回答效果。
3. **每一次改动都在盲飞。** 仅 0924 一天就有 28 条变更记录（CHANGELOG 201～228），其中多条改了 prompt、重试与判定，
   它们让 agent 变好还是变坏，目前只能靠看单局 trace 感觉。
4. **下游要用。** WikiSkill 的门控本身就是"验证集分数严格更高才接受"；B2、B8、C1、E1 的验收也都写成了对照实验。

## 三、测评闭环：两类问题

测评系统自己也会错，而且只有两种错法，必须分开处理，否则"测评集没覆盖到"和"判据本身写错了"会被混在一起排查，越修越乱：

| 类型 | 问题的样子 | 谁来发现 | 怎么修 |
|---|---|---|---|
| **覆盖度问题** | 测评集里没有这类场景，agent 真实翻车了但测评集测不出来 | case 归因（§七）发现"这个失败没有对应的测评样本" | 把 bad case 提炼成新样本，走 §六"数据集"的入库流程 |
| **判据问题** | metric 算错了字段、rubric 定义有歧义、judge 结论和机械判定长期对不上 | 判据自己的回归测试（判据也要有测试用例，不能只靠人读） | 改判据版本号 + 补充判据的单元测试（延续 2026-09-01 的方法论："复核规则要有断言，不能靠感觉"） |

两类问题都必须先归到这张表里的一类，再决定改测评集还是改判据——改错方向是"测评集越改越乱"的常见根源。

## 四、Agent 侧问题来源（归因维度）

一个 task 失败，原因落在以下五类之一，测评报表的归因粒度按这五类分，不再自造一套分类：

| 类别 | 典型现象 | 判别方式（举例） |
|---|---|---|
| **prompt** | 指令没说清楚、字段名和实际 schema 对不上 | 同一模型、同一工具，换一版 prompt 能不能复现失败 |
| **skill** | 某项能力本该被封装成技能但没有，或技能选错了 | 失败集中在某一类任务上，别的类别正常 |
| **模型能力** | 模型本身推理/感知跟不上 | 换更强模型档位，问题是否消失 |
| **工具能力** | 工具本身返回错、超时、接口设计有坑 | 同样调用参数，工具侧直接可复现 |
| **harness 流程** | 重试、超时、状态机切换等流程代码的 bug | 与模型 / prompt 无关，换任何配置都复现 |

这五类是**归因**用的（见 §八成熟度矩阵"归因"列），不是新的 rubric 维度——rubric 回答"这一局好不好"，这五类回答"如果不好，问题出在链路的哪一环"。落地上，直接绑定 §五"过程测评集"的链路模块划分（`sense` / `choose` / `plan` / `decompose` / `judge` / `verify`），因为模块边界本身就是归因边界的候选。

## 五、Task 结构与两类测评集

### 端到端测评集

一个 task 样本必须包含四要素，缺一个都不能算合格样本：

1. **manifest**：起跑前的环境状态清单。**09-25 定（V9）：直接用 checkpoint v2 提供的存档即可，不额外造一层结构化描述**——存档本身已经足够描述"这局从什么状态开始"
2. **prompt**：这局给 agent 的目标指令原文，版本化
3. **可行 behavior**：达成目标的合理路径描述或边界（不是唯一解，是"什么样的过程算合理"），用于约束路径层 rubric 判断，避免"瞎走也算过"或"走了最优路才算过"这两种极端
4. **多维度 rubric**：结果 / 路径 / 效率每个维度拆成若干条目。**v1（标准 L2）按条目打分**（0–2 三档，每档有锚点描述）；到标准 L3 再把条目拆成"是 / 否"二元判断并做人人一致率——二元比连续分数更抗噪、一致率也更好算。红线始终是二元的

由 task 样本组成 episode 级、run 级样本（§六数据集粒度不变）。

### 过程测评集

端到端测评集回答"这局好不好"，过程测评集回答"如果不好，是哪个模块的问题"。样本单位是**单个链路模块的输入输出对**（不是整局），按 §四归因维度里定的链路划分（sense/choose/plan/decompose/judge/verify）逐个建：

- `sense`（感知）：已有 `experiment/observation_check/`，406 帧人工标注，逐字段召回/精确率——直接复用，接入同一份报表
- `judge`：目前没有独立测评集，是本期最优先要建的一个，因为它直接决定"结果层"的可信度（§三的假阳/假阴率就是它的产出）
- `choose` / `plan` / `decompose` / `verify`：暂无，按需补，不强求第一版全部覆盖

过程测评集的样本来源和端到端一样走 §六的入库流程；两者共用同一套 manifest/prompt 概念，只是粒度从"一局"缩到"一次模块调用"。

## 六、数据集（粒度与规矩，沿用并整合旧版 §五/§六）

**样本 = 一个起点 + 目标 + 机械判据 + 类别标签（+ 可选的 rubric）**。起点由 checkpoint v2 提供
（`docs/checkpoint/intent.md` §十、`docs/spec/checkpoint/SPEC.md`），保证每次都从完全相同的"世界 + 状态 + 记忆"起跑。

| 粒度 | 起点 | 终点 | 用途 |
|---|---|---|---|
| **task** | 这一局的 episode 存档 + **回放到该 task 开局**（`restore_run(to_task=…)`；回放段不调模型）；人工设计的样本则是钉死存档直接起一个 task | 这一个 task 结束 | 细粒度能力；成本低、可大量重复 |
| **episode** | 这一局开局前的 episode 存档 | 这一局结束 | 拆解与 task 串联能力；带着前几局积累的记忆 |
| **run** | run 开局的 run 级存档 | run 结束 | 长程推进：多目标、里程碑 |

**多样性要求**：类别覆盖、记忆状态覆盖、难度覆盖。每个版本的数据集附一张覆盖表。

**来源**：① 人工设计：现有 `experiment/tasks.py` 20 条 + 钉死存档，迁为 task 级样本；
② 真机回收：从真实 run 的 task / episode 边界切出 checkpoint；
③ **case 回收（新增，见 §七）**：bad case 经归因确认为"覆盖度问题"后，提炼成新样本入库。

**切分**：数据集可切 train / val / test，切分一经发布就冻结。

**尺子自身的规矩**（不变）：
1. 机械判定是真值，judge 是被测对象，机械判不了的样本显式标"不可机械判定"，不拿另一个模型去猜结果
2. 判定只在评测侧可见，不进决策侧（ROADMAP A4、D1）
3. 同口径才可比：每份报告钉住 git commit、工作区、模型档、`config.py` 旋钮、数据集版本、rubric 版本
4. 盘上 trace 是唯一真相，报表是派生物，删了能重算
5. 只读被测系统
6. 集合冻结，要改就发新版本
7. 不确定性要报出来：重复 k 次、带区间、对比带配对检验
8. 成本与效果同表

## 七、Case 归因与 bad case 资产化

**归因来源**（三条，按成熟度依赖顺序排列，见 §八）：
1. **过程测评集报警**：过程测评集跑出异常（某模块输出偏离历史分布或直接判负）——依赖过程测评集已经建起来（§五），所以是较后期才能用上的来源
2. **业务熟悉**（人工经验）：开发者看单局 trace 凭经验判断"这里不对"——现阶段主要靠这条
3. **真实反馈**：真机跑长程 run 时暴露的问题——目前 L2 长程还没做，这条基本用不上

**流程**：一旦触发报警（不管来自哪条来源），bad case 必须当资产保存，不能看完就丢——具体是：
1. 记录 case 的 trace 引用（不复制数据，只存指针，遵守"trace 是唯一真相"）
2. 归到 §三"两类问题"里的一类：覆盖度问题 → 提炼成新测评样本走 §六来源③；判据问题 → 走判据自己的回归测试
3. 未决的 case（还没判断出是哪一类）先进"待归因"队列，不能悬空不处理也不能直接丢弃

**09-25 定（V11）**：case 是否入库先由人工确认，不做报警阈值自动入库；但**测评产出本身（跑出的报告、bad case 记录、trace 指针）无条件保留**——"入不入数据集"和"测评结果要不要留"是两件事，前者可以卡人工审核，后者不能因为 case 还没定案就被丢弃，否则同一个问题会被反复重新发现。

这条流程目前是 0，是 §九成熟度矩阵里"归因"这一列从 L1 走到 L2 的第一步。

## 八、可观测基座

"盘上 trace 是唯一真相"（§六第 4 条）需要工程上落地，否则只是一句口号。三个要求：

1. **按过滤级别插点**：所有外部调用和状态变化都要插点。**09-25 定（V10）：现有 trace 粒度已经够用，不新增插点分级方案**——不再另设"关键决策点/常规状态变化/debug 细节"这类分级，沿用现状
2. **支持条件检索**：能按模块、按时间段、按类别过滤查询 trace，直接基于现有 trace 字段建索引即可，不依赖新的分级
3. **最小可归因**：插点的粒度要刚好够定位问题所在模块——按 V10 的结论，现状已经满足，暂不因为归因需求反向加埋点

这三条是 §九 V8（trace 是否要补字段）的具体化，也是 §四归因维度、§五过程测评集能落地的前提条件；V10 拍板后，V8 里"事实来源标签、局级墙钟时间"这两项若后续发现真实缺失再单独提，不预先加。

## 九、成熟度矩阵

五个维度分别定义四个等级，作为路线图和阶段验收标准，不是要求一步到 L4：

| 等级 | 观测 | 测评集 | 测评标准 | 回测门禁 | 归因 |
|---|---|---|---|---|---|
| **1** | 只有出入参 | — | — | 手测 | 无归因 |
| **2** | 完整 trace + 支持回放 | 端到端种子集合 | 有 rubric | 自动测试 | 人工分析 |
| **3** | 结构化埋点，支持自动提取 | 分层测评集（黄金集 + 错题集） | 二元化 rubric，人人一致率达标 | — | 归因分层（按 §四五类） |
| **4** | 含"幻觉快照"，可自动判 outcome | case 自动加入（§七流程跑通） | LLM as judge 对齐 | 接入 CI/CD | 机器自动归因 |

**依赖关系**：归因依赖测评集（没有过程测评集，归因分层无从谈起）；标准依赖测评集（没有端到端种子集合，rubric 无的放矢）；门禁依赖标准和测评集都到一定成熟度才有意义接 CI（判据还在变动时接 CI 只会不停红）。五列不是并行独立推进的，测评集和观测是地基。

**现状**（09-25 复核）：观测 L2→L3 之间——trace 有、回放随 checkpoint v2 落地、环境快照已经有（`sense_frame` 每步快照 + `world_snapshot` task 级 + `checkpoint_save` run/episode 级）、`read_events(meta=…)` 条件检索已经有；**唯一缺口是读侧结构化解析层**（`render.py` 只有写侧，每个 `TraceKind` 缺一个对应的 typed parser）和"自动判断 outcome"（依赖 judge 过程测评集判据）。测评集 L0→L1（种子集合还没正式建）；标准 L0（V7 刚拍板 rubric 条目，二元化和一致率校准都没做）；门禁 L0（手测都还没跑通 k=1）；归因 L0（无归因流程）。

**本期 intent 的目标等级（09-25 定，V12）**：

| 维度 | 目标等级 | 说明 |
|---|---|---|
| 观测 | **L3** | 结构化埋点 + 自动化提取，比其余四列更靠前——因为它是其余四列的输入，值得先做扎实 |
| 测评集 | L2 | 端到端种子集合建起来，过程测评集先只做 `judge` 一个模块 |
| 标准 | L2 | rubric 覆盖（§九 V7 四条），二元化和一致率校准留到下一期 |
| 门禁 | L1 | 手测即可，不接自动测试也不接 CI |
| 归因 | L1 | 人工分析，§七流程先人工确认，不做归因分层/自动化 |

观测冲到 L3、其余按矩阵依赖顺序停在 L1/L2，是本期 spec.md 的直接输入。

## 十、范围

**做**
- 数据集的版本化定义（三种粒度；第一版样本从 run 入口起跑、单目标，见 V1）、覆盖表、切分（§六）；
- 端到端测评集：manifest / prompt / 可行 behavior / rubric 四要素齐全的样本（v1 从 run_begin 存档起跑，§五）；
- 过程测评集：优先建 `judge` 模块的测评集，`sense` 直接复用现有 `observation_check`（§五）；
- 批跑入口：给定数据集版本、重复次数、配置，从存档起跑并落盘；
- 机械判定器；rubric 框架（含模型评分的校准流程）；
- 三个维度（结果/路径/效率）的汇总报表，机器可读（jsonl）+ 人可读（md 或 html）；
- case 归因与 bad case 资产化的最小流程（§七，先到"人工分析 + 记录指针"，不强求自动化）；
- 第一份跑通报告：当前 main 在第一版数据集上、k=1 的报告（不作正式基线；正式基线待 k>1）。

**不做**
- 在线测评（真实 run 的实时监控/报警）——本期完全不讨论，留后续 intent；
- CI 回归门禁——按 §九 成熟度矩阵，门禁依赖标准和测评集先到 L2/L3，本期不接，等判据稳定后另议（不是永久不做，是排在后面）；
- 前沿模型参考线（A3）；
- L2 长程里程碑评测（本期只登记）；
- 可视化看板 / 服务；报表是文件；
- 归因自动化（L4）——本期先到人工分析（L2）；
- 测评期间不调参刷分。

## 十二、成功的样子（intent 层验收）

1. 一条命令跑完一个数据集版本，产出一份钉住口径的报告，覆盖结果 / 路径 / 效率三层、task / episode / run 三种粒度；
2. 报告给出当前产品 k=1 的第一份跑通结果，以及 judge 的假阳 / 假阴率（正式基线在 k>1 时给出）；
3. 两份报告可以对比，并给出配对检验结果；
4. 模型评分的 rubric 条目附带与人工标注的一致率；
5. 报告里每个数字都能从盘上 trace 重算出来；
6. 出现的 bad case 都能落到"覆盖度问题"或"判据问题"其中一类，并有对应处理记录，不悬空；
7. WikiSkill 复现可以直接把"在 val 集上跑一遍并取分"当作门控调用。
