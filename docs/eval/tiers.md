# 评测的三档与冻结（定稿 2026-10-28，用户确认）

> 本文是"三档是什么、冻结是什么、规划器给的条件怎么用"的唯一依据。`docs/eval/mid_tasks/intent.md` 第二节按"完成范围"定义三档，是旧口径，以本文为准。
> 关联：`docs/eval/datasets.md`（现行数据集清单）、`docs/eval/long_tasks/intent.md`（长期任务）、`docs/eval/short_frozen/`、`docs/eval/mid_dataset/`。

## 一、两条正交的轴

| 轴 | 回答的问题 | 性质 |
|---|---|---|
| **分层**（短期、中期、长期） | 任务本身是什么性质、边界谁来定 | 数据集的性质，写在任务里 |
| **冻结** | 为了隔离变量，把哪一层的输出固定下来 | **评测手段**，是一次评测的运行设置，不是任务的性质 |

两条轴互不决定对方。同一份任务可以冻也可以不冻，冻结只是为了让被测的那一层单独暴露出来。

## 二、三档的性质

| 档 | 任务的性质 | 怎么写任务 | 边界谁定 |
|---|---|---|---|
| **短期** | 边界对齐脚本 | 以**最能匹配脚本的口径**写：一个 task 就是脚本能干净完成的一件事（治疗、买东西、抓捕、过门），起止天然清楚 | 任务本身 |
| **中期** | 边界由规划器给出 | 规划器把 run 拆成若干 episode，每个有明确的起止；任务依赖跨 episode 的信息 | 规划器 |
| **长期** | 开放、有干扰 | 目标开放，途中会插进别的事件；靠上一个 run 留下的记忆（或探索）才能更快完成 | 没有预设边界；**按干扰程度分层** |

### 长期的干扰分类（用来给长期分层，也给其他样本标注）

| 类型 | 实验里见到的例子 |
|---|---|
| ① 确定性脚本事件 | 往北走被大木拦住带去研究所；研究所对白；选宝可梦菜单 |
| ② 强制战斗 | 选完宝可梦后与对手的对战（败了也能继续走出研究所） |
| ③ 随机事件 | 1 号道路的野生遭遇（随节奏变化，同一空转帧下重复结果相同，不是独立样本） |
| ④ 空间障碍 | 1 号道路中段的墙要绕行 |
| ⑤ 会动或会拦路的对象 | 常青市商店里的移动顾客（位置取决于时间线）；真新镇有一个会走动的 NPC，实验里没能稳定接近，是否构成干扰待核 |

长期各层按**干扰逐层叠加**（终点越远，经过的干扰类型越多）：

| 长期层 | 终点 | 经过的干扰类型 |
|---|---|---|
| 一 | 走出自己的家（map 0） | 无 |
| 二 | 拿到第一只宝可梦 | ① |
| 三 | 离开真新镇（map 12） | ①、②（⑤ 待核） |
| 四 | 到达常青市（map 1） | ①②③④（⑤ 待核） |

现行其他样本的标注：中期 M1 含 ③④，M4 含 ⑤，M3 的捕获含③（随机数）。标注写进 `docs/eval/datasets.md` 的已知局限里，难度因此可解释：哪一层差，差在哪一类干扰。

## 三、冻结

冻结只是评测手段。三个冻结点：

| 冻结点 | 固定什么 | 隔离出的被测对象 |
|---|---|---|
| 冻结 task 表（短期常用） | 每个 episode 要做的 task 列表 | choose 与 task 记忆，不受 decomposer 影响 |
| 冻结 episode 目标表（中期常用） | run 拆成的 episode 目标 | episode 内的执行与跨 episode 记忆，不受规划器影响 |
| 冻结记忆种子（长期用） | 第二个 run 起跑时的记忆目录 | 读过往 run 记忆的能力，不受第一个 run 成败影响 |

放开冻结就是被测对象变成上一层：不冻 task 表，被测的就包含 decomposer；不冻 episode 目标表，被测的就包含规划器。

**已知的建模债**：目前代码里冻结与 `tier` 字段绑定（`tier` 决定两个冻结开关，`evals/agent_short_goal_run/solver/runner/one.py`），所以为了做"自由拆解对照"才留了 `v20261021_retest5` 这个无 `tier` 的旧格式版本。目标是把冻结改成运行设置（默认值由档推出，实验时可覆盖），同一份数据集想冻就冻、想放开就放开，`retest5` 届时就没有存在的理由了。暂不动代码，先记账。

## 四、规划器给出的条件只用于评测

规划器（也包括分解器）是 LLM，它给出的起止条件、成功标准**不能保证正确**，所以：

1. **真值只来自我们自己写的机械判据**（读游戏内存与账本，人写的，已验证）。run 级判据（`walk_to_pallet`、`heal_buy_return` 等）决定通过与否。
2. 规划器给出的起止条件是**被测对象**：评测时拿它与机械真值对比，算"规划器给的条件准不准"之类的指标；它**不参与运行控制，不决定通过与否**。
3. 数据集里若存每个 episode 的起止条件，那是我们写的**参考答案**，只用来评测，不喂给被测系统。冻结的目标表是我们写的数据，不是规划器的输出。
4. 落码时的断言点（实现另排，见 686 之后的任务）：
   - 判据函数的输入只能是账本与内存读数（`RunStream` 的帧与观察），不读规划器或分解器的输出字段；
   - 通过与否只由已登记的机械规则给出，模型打分只能产出指标，不能改通过与否；
   - 冻结目标表与 task 表只能来自数据集文件，不能来自上一次运行的规划结果。
