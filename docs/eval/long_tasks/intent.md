# intent —— 长期任务：开放探索与跨 run 记忆

> 流程位置：**intent.md**（2026-10-28 重写，用户已确认主要决定）→ spec → plan → 落码
> 关联：`docs/eval/tiers.md`（三档的性质、冻结、干扰分类；以它为准）、`docs/eval/mid_tasks/intent.md`、`docs/eval/datasets.md`、`docs/eval/task_boundary/intent.md`、ROADMAP F13、B15、B16
> 前置实验结果：`experiment/long_verify/`（不入库）：冷启动、卧室起点、完整路线、文字线索普查。

## 一、一句话意图

长期任务是**开放探索**：开局在新游戏的卧室里，什么都不知道，目标像"离开真新镇"；线索只在探索之后才出现，或者由上一个 run 留下的记忆提供。评测的是第二个 run：从**同一个起点**重新开始，带着由第一个 run 产生的、冻结的记忆，看它能不能更快、更少走冤枉路地完成同一个目标。

## 二、为什么

1. 短期考一个 episode 内的 choose 与 task 记忆，中期考一个 run 内跨 episode 的记忆；"过往 run 索引"这条读取路径（`_read_run_index`、`RunMemory.index`）至今没有样本考到。
2. 记忆有用的原因必须是**游戏状态里本来就没有、只在上一个 run 里探索过才知道**的信息（研究所在哪、必须先被大木拦住、要选宝可梦、会有一场对战），而不是我们把本来看得见的东西藏起来。
3. 实验已确认这条线在原作里天然成立：必经事件自带门禁，线索（家里的电视、路牌、NPC）在探索中才出现。

## 三、做什么

### 3.1 起点（已核实）

新游戏卧室存档：map 38 (3,6)，队伍与背包为空，钱 3000，`D74E=0x00`。**由 ROM 冷启动按固定按键序列生成**（5 次重复终局哈希一致，`95b2cabd…`），数据集里附构建脚本（按键序列加哈希核对），不是手工保存的文件。仓库里现有的所有存档都不是新游戏开局。

### 3.2 难度分层（同一个起点，目标的终点不同，oracle 步数为实测累计值）

| 层 | 目标（给 agent 的文字，不含地名答案） | 机械判据 | oracle 步数 |
|---|---|---|---:|
| 长期·一 | 走出自己的家 | 到达 map 0 | 24 |
| 长期·二 | 拿到你的第一只宝可梦 | 队伍至少一只 | 131 |
| 长期·三 | 离开真新镇，一路向北走到镇外 | 队伍至少一只，且到达 map 12 | 238 |
| 长期·四 | 离开真新镇，到达北边的下一个城镇 | 到达 map 1（含此前所有） | 334 |

- 先建**第三层**（主）；其余层只是同一起点加不同的目标与判据，成本很低，随后按需加。
- 游戏自带门禁：不拿宝可梦，往北走会被大木拦住带去研究所，所以"找研究所、选宝可梦、过对战"是游戏要求的，不是我们设的；对战败了也能走出研究所（已测败北分支）。
- 目标文字不给地名答案；如果写地名，用游戏里实际出现过的英文名（进城前 1 号道路的路牌已写出 `VIRIDIAN CITY`）。

### 3.3 两个 run 的机制（用户确认：不做中途恢复）

- **run 1（产生记忆，一次性）**：用真实模型从卧室存档跑第三层或第四层的目标，记忆流水线照常产出这个 run 的记忆；**生成一次、人工审、冻结**，冻结物 = 记忆目录（带哈希）。run 1 成败不影响评测，它的记忆里有什么就是什么（走了冤枉路也是真实的记忆）。
- **run 2（被评测）**：**全新启动**，从同一个卧室存档起，memory 服务的根目录里放着冻结的 run 1 记忆；评测只跑 run 2。
- **harness 不做真正的恢复**：只在启动时按存档（`.state`）恢复世界；不做图内的中途恢复；memory 只是"指向一个新的记忆仓库"（评测里实现为起服务前把冻结目录复制进临时根，保证每次评测隔离、种子不被改写）。

### 3.5 指标（全部可机械计算）

- 成败：判据（`pass_at_k`，重复 3 次）。
- 步数曲线：到各里程碑（下楼、出家门、进研究所、选宝可梦、过对战、出镇）的步数，里程碑由地图编号与队伍人数判定；与 oracle 对比，同时与"不带种子"的同一样本对比。
- 无效步数：撞墙（`blocked`）次数、重复读已读过的对象的次数。
- 记忆使用证据（读取与使用分开记）：run 2 是否读取了 run 1 的索引；早期决策里是否直接去了 run 1 记忆里出现过的地点。检索指标（Recall@k、MRR）等有了检索真值再报。
- 预算：run 2 的 `max_steps` 取 3×oracle（第三层约 720）；`agent_steps / oracle_steps` 单列，不与其他档直接比较。

### 3.6 消融（评测运行设置，不是任务设计的一部分）

同一份数据集跑两遍：带冻结记忆种子、不带种子（其余完全相同）。差值就是跨 run 记忆的贡献。

## 四、不做

- **不做真正的恢复**：不做 harness 的图内中途恢复、不用 checkpoint 存档当起点；只做启动时的世界存档恢复。
- 不做三个以上的 run；不做 run 之间的遗忘；不测记忆写入质量本身（那是摘要节点的量表）。
- 不手写记忆；不把"藏起本来看得见的东西"当成需要记忆的原因。
- 包裹交付、顾客台词那条（原 L1、L2）**暂时搁置**：包裹的托付对话没有说研究所在哪，记忆里本来就没有收件人的位置；顾客台词留待探索线定稿后再看。
- 不改现有 20 条短期样本与中期 M1 到 M5。

## 五、待确认

1. **冻结记忆由哪个模型产出（用户已定：deepseek4.1flash，choose、decompose、plan、summary 全用它，这样种子里不混别的模型的口味）**：完整的模型标识字符串以评测配置里的写法为准，待用户给出；一次真实 run 的步数估计是 oracle 的几倍（第三层 238 步，约几百到一千多个决策），一次性花费。成功标准事先写死：最多跑 5 次，取第一次到达判据的那次冻结，5 次全部留档，不事后挑选。
2. **是否移除 checkpointer 的图内恢复与存档体系**：用户决定"不做真正的恢复"，现有 `pokemon_agent/harness/checkpoint/`（checkpointer、restore、saver、manifest）、trace 的血缘与 `checkpoint_restore` 账、评测 scorer 对分支的自动检测、memory 服务的 `restore` 管理接口、`docs/checkpoint/` 都与它有关。先做一次只读盘点（哪些要删、哪些要留作启动时恢复），再写移除 spec；这是独立的任务，不挡长期数据集的 spec。
3. 先建哪几层（建议先第三层）。

## 六、成功的样子

- 卧室起点可由构建脚本复现且哈希可核；冻结记忆哈希可核；oracle 的 run 2 在带种子设置下通过判据。
- 同一批 agent 在带种子与不带种子两种设置下，run 2 的成功率或步数有可测的差，证明任务确实在考跨 run 记忆。

## 评测入口调查结果（2026-10-28）：第二个 run 能不能带着第一个 run 的记忆起跑

**现状：不能，但缺口小。** 读 `evals/common/eval_services.py`、`evals/agent_short_goal_run/solver/solver.py`、`solver/runner/one.py`、`evals/common/overlay.py` 与 `harness/run/perceive/read_plan_context.py`：

- 每条样本启动一套**独立**的 memory 服务，根目录是 `tempfile.mkdtemp` 临时目录，里面只放从仓库 `memory/knowledge_memory` 复制来的知识 Markdown；样本结束整个目录 `rmtree`。所以第二个 run 起跑时 memory 里除知识外是空的，第一个 run 的记忆也没有被导出。
- 好消息：规划层读"别的 run 的记忆"这条路本来就在（`_read_run_index` 读到的 run 记忆里滤掉 `run_id == 本 run` 的，其余都作为 run 索引），所以只要第二个 run 的 memory 根里放着第一个 run 的记忆文件，现有读取逻辑不用改。
- 需要补的三处小改动（留给长期数据集的 spec）：
  1. `eval_services` 增加可选的 `memory_seed`（一个目录，起服务前把它的内容复制进临时根的 `memory/`，做法同 `_prepare_knowledge`），每条样本仍然隔离，结束仍然清理；
  2. 数据集样本新增可选字段 `initial_memory`（相对路径加 sha256，仅长期档允许），加载时核对哈希，`solver` 把它传给 `eval_services`；
  3. 生成种子需要把第一个 run 的 memory 根在清理前导出：`eval_services` 增加可选的"退出前导出 memory 根到指定目录"。

## 设计原则（用户确认）：不靠"中途藏起记忆"制造需要

长期任务里，第二个 run 需要记忆，必须来自**游戏状态里本来就没有、只在上一个 run 里出现过的信息**（例如包裹的收件人只在托付对话里说过一次，之后画面、内存、背包里都没有），而不是我们把本来看得见的东西（知识库条目、地图连接）临时关掉。因此：

- 包裹交付**不再作为长期任务**：托付对话没有说明研究所在哪，记忆里本来就没有这条信息（2026-10-28 用户指出）；它只在整段早期游戏里才讲得通。
- 记忆开 / 关对照是评测运行设置里的消融（同一份数据集跑两遍），不是任务设计的一部分；任务本身不含"被藏起来的东西"。
- 包裹交付的前置实验取消。

## 知识库按数据集配置（用户确认，2026-10-28）

长期任务是开放探索（开局在卧室、不知道任何地点），所以**不能让知识库把地图事实告诉 agent**。现有知识里 `map_connections`（常青市、1 号道路、真新镇、研究所的连接关系）是为中期 M1 加的，知识库按地图与目标文字召回，长期任务开局在卧室时它会把整条路线交出去。处理方式：

- **知识库由数据集配置**，不是运行中途关掉。评测起服务时 `knowledge_source` 本来就是每次传进去的（`solver.py` 目前对所有样本都传仓库 `memory/knowledge_memory`）。做法：样本新增可选字段 `knowledge_exclude_topics`（知识原子 `metadata.topic` 的列表），评测复制知识文件进临时根时跳过这些主题；长期样本写 `["map_connections"]`，中期样本不写（保持现状，M1 仍然有路线知识）。字段与"知识主题必须真实存在"的校验放进长期数据集 spec，和 `initial_memory` 一起做。
- **新增一条只讲方法、不给答案的知识**（暂定主题 `explore_and_read`）：怎么探索——面向路牌按 `a` 读、和遇到的 NPC 说话并记下地名人名、新地图先找出口、走不通就换方向别反复撞墙、新城镇先看路牌与中心商店位置。它进全局知识库（对所有数据集可见）。**内容在冷启动实验的文字对象普查结果出来后再定稿**：游戏里到底有没有路牌、路牌写什么，以实验为准，知识正文不得承诺游戏里不存在的东西。
- 长期数据集的清单里要写明它使用的知识配置（排除了哪些主题），这样"知识不同"是数据集设置，不是隐藏。
