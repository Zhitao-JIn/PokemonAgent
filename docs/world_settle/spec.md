# spec —— 按键后画面判稳：一条规则，参数按场景

> 状态：设计已定，实现待 `feat/step-observation` 合并之后（世界侧改动，不属于那条分支）。
> 依据：`experiment/probe_settle_report2.json`、`probe_settle_report3.json`（22 个存档 × 12 次按键，真值 2400 帧，两次采集逐字节一致）；设计讨论 2026-10-28。
> 编号：待分配（合并后）。

## 一、结论（数据）

按生产起点（按键后先过 60 帧再每 4 帧采样）看现行规则（连续 24 帧静止）：判稳之后画面又变的"读早"共 18 次，分类为：对话区没变而 HP 等其他区域变 16 次、整句旧文字清空 2 次、**文字续打（读到半截）0 次**。读早全部集中在战斗类与治疗，野外、对话、菜单/商店为 0。动画中多按 a 无影响，所以读早只会多出 `choose` 请求，不会损坏状态或漏掉台词；调大静止帧数用游戏时间换模型调用，划算。

各场景类别、不同静止帧数 Q 的结果（读早次数 / 平均真实等待帧 / 最大等待帧）：

| 类别（按键数） | Q=24 | Q=120 | Q=180 | Q=240 | Q=360 |
|---|---|---|---|---|---|
| 其余：野外、对话、菜单、商店（173） | 0 / 93 / 196 | 0 / 189 / 292 | 0 / 249 / 352 | 0 / 309 / 412 | 0 / 429 / 532 |
| 战斗类（67） | 16 / 175 / 332 | 6 / 288 / 544 | **0 / 367 / 680** | 0 / 427 / 740 | 0 / 547 / 860 |
| 治疗（24） | 2 / 109 / 148 | 2 / 205 / 244 | 2 / 265 / 304 | 2 / 325 / 364 | **0 / 474 / 808** |

总预算 T：以上推荐值下最大等待 680（战斗）与 808（治疗）均小于 900；Q=480 的战斗类已有 11 次超过 900。

## 二、决定表

| 编号 | 决定 |
|---|---|
| W1 | **规则只有一条**：每次按键之后（单键动作与脚本内每键同一个入口），推进到"解码屏幕文字（忽略 `▼`）加玩家位置"连续静止 Q 帧，总真实帧预算 T；预算用完仍未静止，返回 `settled=False`（不当稳定），`Abort` 与否仍由现有策略 `abort_on_timeout` 决定。采样间隔沿用 4 帧 |
| W2 | **参数按场景取**：默认 `(Q=24, T=900)`；战斗类 `(Q=180, T=1200)`；治疗 `(Q=360, T=1200)`，治疗由治疗脚本通过自己的 `StableWait` 声明，不在等待函数里按地图或对话判断。T 在战斗与治疗放到 1200 是留余量（最大观测 680 与 808） |
| W3 | **场景就是世界已有的 `TaskScene`**（`world/scene.py::classify_scene(text, mem)`，纯函数，吃同一次解码的 `ScreenText` 加几个内存字节）。战斗类 = `{battle, battle_menu, battle_switch}`。**粘性判法**：这次按键前最后一次观察的场景，或等待期间任何一次轮询的场景属于战斗类，整次等待按战斗类处理，不降回去（战斗结束、画面已退出战斗的那几次轮询也要算战斗类） |
| W4 | **一次轮询一次解码**：同一份 `ScreenText` 同时用于比较变化与 `classify_scene`；适配器里把当前帧的解码结果缓存到下一次 `tick` 之前，循环里再读不重复解码 |
| W5 | **删除**固定推进：`pyboy_world.py` 的 `WITHIN_ACTION_FRAMES`（单键后固定 60 帧）与 `AFTER_ACTION_FRAMES`，以及 `settle_screen` 的 `minimum_frames`；单键动作与脚本内每键都走同一个等待函数。按键本身的按下与释放帧数不变 |
| W6 | **`settled` 的含义**：画面连续静止 Q 帧，不是"游戏做完了"。紧凑观察里的 `settled`、`changes()` 对 `settled=False` 的处理（不产出对话行）不变 |
| W7 | **不做**：不引入 `▼` 门控（一段对话的最后一句没有 `▼`，会被永远判不稳，丢掉关键台词）；不引入存档窥视；不按坐标或地图编号区分场景；不给不同场景写不同的完成信号 |
| W8 | **可选保险（等真出现问题再做）**：`changes()` 产生对话行时，后一次文字以前一次为前缀则视为同一行没打完，不单独产出前一次的半截行；现有 2400 帧数据里"文字续打"为 0 次，暂不需要 |

## 三、验证口径（实现时）

1. 分类校验以"没有误报"为准：非战斗存档的按键 0 次被归为战斗类；存档类别标签不是真值（战斗存档后几次按键已退出战斗，场景全程是 `walk`，被归为其余是对的）。
2. 回放：用保存的 2400 帧真值离线跑新规则，结果必须等于上表（读早 0、最大等待在预算内）；离线脚本留在 `experiment/`。
3. 单元测试用合成的轮询序列测等待函数：静止满 Q 返回；中途变化重新计数；超时返回 `settled=False` 与等待帧数；战斗类粘性；治疗脚本的覆盖；解码在一次 tick 内只发生一次（用计数的假控制台证明）。
4. 世界侧现有测试（脚本、步骤、MCP）保持绿；`oracle_steps` 等依赖等待时长的实验数据在实现后用最终参数重跑一次。

## 四、影响面与风险

- 影响面：`world/pyboy_world.py`、`world/scripts/screen_wait.py`、`world/scripts/timing.py`、`world/scripts/engine.py`（`_press`）、`world/console_adapter.py`（解码缓存）、治疗脚本的策略、对应测试。
- 风险：游戏里每次按键多过数秒（战斗约 6 秒、治疗约 8 秒），NPC 与计时类事件随之往前走，世界状态与改前不同；对确定性无影响（同输入序列同结果），但已有的 `oracle_steps` 与存档派生数据要用新参数重跑。
- 非目标：不调整 `▼` 的比较口径；不改观察结构；不改预算语义（一个决策仍算一步）。
