# intent —— task 层感知按界面分类；商店购买与起名机械接管

> 流程位置：**intent.md** → spec.md → plan.md → PR → production
> 状态：**草案**（2026-09-26）；第九节两项已定（见文末）；探测结果见 `p0-findings.md`
> 上游：`docs/eval/p0-findings.md` 第七、八节，CHANGELOG 261–263，读屏测评 `eval_results/screen/20260926-100021`
> 本文写的每个内存 / ROM 来源都标了**实测**与否；没实测的，spec 前补测，补不到就不用。

## 一、一句话意图

**task 层每一帧先按内存和屏幕缓冲把界面分类，每类给自己的观测和动作空间。常规界面照旧一键一决策；
商店购买列表与起名键盘两类由 JEV 说出参数（买什么、买几个 / 起什么名），程序机械执行到底。**

## 二、为什么

1. **读屏测评显示整屏原样不是万能的**（451 帧，解码直出全对 418 → 模型读后 417）。模型在切不全的界面补回一些
   （数量 0/5→5/5、切不全的选单 0/6→3/6），也在解码本来对的地方改错一些；两个真问题都出在模型读整屏：
   数量框帧把 `▷` 那一层（BUY/SELL/QUIT、商品列表）当成当前选单；队伍列表把 `▶` 对错一行。
2. **这两类界面需要的是"执行"，不是"阅读"。** 购买要"移光标 → 选中 → 调数量 → 确认 → 付款"一长串，起名要在
   9 列键盘上逐字点——让 JEV 一键一决策，步数多、每一步都可能读错；交回 episode 也没用，episode 拆出的 task
   回到这里还是做不了。
3. **信息源大多是确定的**：商店的完整清单、单价、金钱、背包都在内存 / ROM 里（第四节表），不必靠屏幕切。

## 三、task 链（改完以后）

每一圈：**感知 → 停摆与记忆 → 判定 → 决策（JEV）→ 执行**，与现在同构；变的是感知给什么、JEV 输出什么、执行怎么展开。

1. **感知**（不调模型）：读内存与屏幕缓冲 → **按界面分类**（第四节）→ 按类组观测。
2. **停摆检测 / 单步记忆 / 物体事件**：不变；物体事件的对话闸门由"做过视觉"改为"这一帧的文字读过"（task 层解码
   读过，episode 层视觉读过）——现在 task 层的对话事件一条都记不下来。
3. **判定**：不变；prompt 引用与决策同一段"屏幕读法说明"（`▷` 是上一层、`-` 是空招式位）。
4. **决策（JEV）**：常规类输出 `{"action": "up"}`；`shop_list` 输出 `{"action": "buy", "item": …, "quantity": …}`
   或 `b`；`naming` 输出 `{"action": "enter_name", "name": …}`。解析器按这一类的动作空间校验参数，不合法走现有的
   重试纠正。
5. **执行**：常规类按一个键；`buy` / `enter_name` 由 tool 层展开成按键，**每一步读内存核对**，对不上就停、记一条
   执行失败，交给下一圈的判定与决策，不盲按。

## 四、界面分类与各类观测

**画面字段二选一**（合并 `walk_map` 与 `screen`）：屏幕上有字 → 只给整屏原样；没字（走路）→ 只给 `walk_map`。
`neighbors` / `landmarks` / `where` 照常给。战斗里不再给全是 `#` 的 walk_map。

| 类 | 怎么认 | 观测 | 动作 |
|---|---|---|---|
| 走路 | 屏幕没字 | 位置、朝向、四邻、地标、walk_map | 按键全开 |
| 对话 | 严格对话帧（已实现） | 对话 + 整屏 | 只有 `a` |
| 选单 | `▶` 在有边框的框里、切得全 | 选项、光标、排布、附注 + 整屏 | 按键全开 |
| 队伍列表 | `▶` 在第 0 列、无框 | 昵称、光标 + 整屏（解码按固定格式切，新增） | 按键全开 |
| 其余 | 以上都不是 | 整屏原样 | 按键全开 |
| **`shop_list`** | 待定：MONEY 框 + `¥` 列表（缓冲特征），或内存变量（待探测） | 见下 | `buy(item, quantity)`、`b` |
| **`naming`** | 待定：键盘版式（缓冲特征），或 `wNamingScreenType`（待探测） | 见下 | `enter_name(name)` |

**`shop_list` 的观测**

| 字段 | 来源 | 实测 |
|---|---|---|
| 完整商品清单 | 内存 `wItemList` 0xCF7B（数量 + 物品 ID + 0xFF） | ✅ 4 项与屏幕一致 |
| 商品名 | ROM `ItemNames` 0x472B，按 ID | ✅ |
| 单价 | ROM `ItemPrices` 0x4608，3 字节 BCD（`wItemPrices` 0xCF8F 存表指针） | ✅ 200/100/200/250 与屏幕一致 |
| 金钱 | 内存 `wPlayerMoney` 0xD347，3 字节 BCD | ✅ |
| 背包已有 | 内存背包 0xD31D / 0xD31E | ✅（E0） |

**`naming` 的观测（最小可执行）**

| 字段 | 给谁 | 来源 | 实测 |
|---|---|---|---|
| 给谁起名 | JEV | 屏幕标题解码（`YOUR NAME?` …）；`wNamingScreenType` 0xD07D 旁证 | ✅ 主角；⚠ 对手、宝可梦未测 |
| 已输入的名字 | JEV | `wStringBuffer` 0xCF4B（屏幕上也有） | ✅ |
| 键盘光标 | 只给执行器 | `wMenuCursorLocation` 0xCC30 | ✅ |

名字只允许大写字母（键盘默认大写，执行器不切大小写）；不读长度上限——执行器每输入一个字核对
`wNamingScreenNameLength` 0xCEE9 是否 +1（✅ 实测 0→1→2），不加即到上限，停手按 END 并在账上记"名字被截断"。

## 五、机械接管的范围

- **购买**：从选中商品一路到付款。光标移到商品（`wCurrentMenuItem` + `wListScrollOffset` 0xCC36，⚠ 翻页未实测）
  → a → 按 `wItemQuantity` 0xCF96 调到目标数量（✅ 实测上键 1→2→3）→ a → YES → 按完致谢台词 → 回到列表停。
  钱不够、数量超上限（`wMaxItemQuantity` 0xCF97）在解析时就拒，不进执行。
- **起名**：接管到按 END 为止。
- 两者执行完都回到正常循环，下一圈照常感知、判定。

## 六、要动的地方

| 层 | 改什么 |
|---|---|
| world | 界面分类；队伍列表解码；`shop_list` / `naming` 的读数；画面字段二选一；WorldTool 暴露分类接口 |
| tool | `buy` / `enter_name` 的展开与逐步核对；动作空间按类给 |
| brain | 解析器接受带参数的动作，按类校验 |
| prompt | `decide_action` 按类渲染观测与动作说明；共用"屏幕读法说明"片段（决策、判定、校验、总结、拆解共用） |
| harness | 物体事件对话闸门；宏动作在一圈里算"一步" |
| trace | **待你确认**：宏动作记一条带参数的动作账，挂展开的按键序列与逐步核对结果（不记成十几条 `press_key`） |
| memory | `ActMemory` 一条宏动作一条（前后两帧） |
| 测评 | 读屏测评改为"分类准确率（451 帧全测，每帧加标种类：规则预标、你在核对页校）+ 常规类读取准确率"；
`shop_list` / `naming` 只看分类，另从存档出发测"给定参数能否执行到位"；并入三处小改：打分忽略 `-`、空对话框 9 帧改标 `none`、起名键盘不再按读取打分 |

## 七、不做的

- 不给 task 层加视觉；未知界面不交回 episode（交回也做不了），给整屏原样尽力读。
- 不做"整屏只给整屏、去掉 options/cursor"——读屏测评显示字段在 A 类界面上比模型读整屏稳。
- 商店卖出（SELL）、PC 存取、背包丢弃的数量框：本期不接管，照旧常规决策（数量从整屏读，已 5/5）。

## 八、spec 前要补的探测

1. `shop_list` / `naming` 的判别依据（缓冲特征 vs 内存变量），在 observation_check 406 帧 + 今天 45 帧上核零误判。
2. 对手、宝可梦昵称两种起名界面（开机新游戏走到对手起名；抓一只宝可梦进昵称）。
3. 商店列表翻页（商品 > 4 项的店）与购买全流程每一步的内存变化。

## 九、已定（09-26）

1. **宏动作记一条账**（购买、卖出、PC 存取丢、起名同理）：一条带参数的动作账，挂展开的按键序列与逐步核对结果。
2. **一切多级选择都机械接管**（推翻第七节第三条，数量框都在宏里）。接管场合与宏：
   - `naming` → `enter_name(name)`，只许大写字母，输完按 START 提交；
   - `shop_items`（MONEY 框在屏的一切帧）→ `buy(item, quantity)` / `sell(item, quantity)` / `quit()`；
   - `pc`（一打开起）→ `withdraw_item` / `deposit_item` / `toss_item(item, quantity)`（重要道具不弹数量框）、
     `withdraw_pokemon` / `deposit_pokemon(pokemon)`、`change_box(n)`；不开放放生；
   - `bag`（野外一打开起）→ `use(item[, pokemon])` / `toss(item, quantity)`；
   - `battle_menu`（战斗里的选单）→ `fight(move)` / `switch(pokemon)` / `use_item(item[, pokemon])` / `run()`；
   - `faint_switch`（"Bring out which POKéMON?"）→ `send_out(pokemon)`；
   - `party`（野外队伍列表）→ `switch(a, b)` / `field_move(pokemon, move[, destination])` / `stats(pokemon)`
     （`stats` 停在能力页，交回常规场合 `pokemon_info`）；
   - `learn_move` → `forget(move)` / `skip()`（提示文案从 ROM 核过，屏上未见过）。
   初态时宏要的参数都在内存里（实测见 `p0-findings.md` 第六节）。以后遇到电梯楼层、奖品兑换、售货机、NPC 交换，按同一形状加。
3. **按场合分，不按控件分**（人在哪、在做什么决定能召回哪些知识）：
   - 常规：`walk` / `dialog` / `battle`（战斗里选单以外的帧：文字、单层 YES/NO、结算）/ `shop`（商店里还没打开买卖菜单：
     走动、和店员说话，按图块集 MART 认）/ `pokemon_info`（能力页、图鉴条目页）/ `start_menu`（开始菜单本身、图鉴目录、
     训练家卡片、选项）/ `title` / `transition`（空框、淡入淡出、开场图形）；
   - 接管：见上一条；单层的 YES/NO（治疗、要不要取名）不接管；
   - **不设单独的 `quantity` 场合**：数量框一律属于所在场合的宏动作。
4. **`walk_map` 与 `screen` 互斥**：屏上有字只给 `screen`，否则只给 `walk_map`。
5. **起名观测最小化**：给谁起名、已输入的名字、键盘光标（光标只给执行器）。
6. **宏不设子状态，开跑前按 B 回初态**（实测见 `p0-findings.md` 第五节）：
   - 每个宏只自带一个"是否在初态"判断（测评里的 `at_start`）：**本场合的主菜单画着、实心 `▶` 在上面、屏上没有任何空心 `▷`**。
     主菜单：起名键盘；`▶BUY / SELL / QUIT`；选哪台 PC；背包列表；`▶FIGHT / PKMN / ITEM / RUN`；队伍列表；
     "Delete an older move…" 的 YES/NO。只看三角不够：战斗的招式列表 / 背包 / 换人列表、PC 的各级菜单都整块盖住上一层，不留 `▷`；
   - 判初态前先等画面稳定（缓冲连续几次不变），否则会把重画中的帧当成"不在初态"，多按一次 B 就退出场合；
   - 开跑前循环：在初态 → 停；已不在本场合 → 放弃并交回 task 层；否则按 B、轮询到画面稳定，再判；设次数上限；
   - 宏跑完回到初态或离开本场合（战斗出招后进入战斗文字），交回 task 层重新感知；
   - 中途核对失败同样按 B 回初态，trace 那一条记下停在哪一步；买卖是否已成交看钱与背包，不靠步骤推断。
7. **参数校验放执行层，brain 只做解析**：
   - brain 把 JEV 输出解析成类型化动作，只查动作名在本场合动作空间里、字段类型对；解析失败让 JEV 重出，不碰游戏；
   - 宏自己校验语义前提（商品在表里、钱够、有 PP、数量 1–99、背包有空位…），用**回初态之后**读到的内存；
     不合法一个键都不按，返回类型化的拒绝（错误码 + 原因），brain 把原因附在下一轮观测里交给 JEV；
   - JEV 输出是外部输入，校验写成运行时检查返回错误，不用 `assert`；宏内部"按了这一步应出现数量框"才是 `assert` 契约。
8. **宏调用的 trace**（trace 是唯一落盘处）：每次宏调用记一条，含三部分：
   - 调用与结果：场合、动作、参数、结果（成功 / 被拒 / 中途放弃 / 离开场合）、错误原因；
   - 状态摘要：钱、背包、PC 的前后变化，一行；
   - 逐步明细（**每次都记**，不只失败时）：每步按键、等待帧数、期望变化、实际读到的、核对结果、停在哪一步。
9. **宏是原子的，跑完再判**：宏执行中途 judge 不打断；宏结束（成功 / 被拒 / 中途放弃 / 离开场合）后，judge 才看结果决定是否交回 episode。宏内部失败自己按 B 回初态。
10. **战斗文字由执行器自动推进**：`battle_menu` 的宏出招 / 换人 / 用道具 / 逃跑后，执行器自动按 A 推进战斗文字，直到下一个接管场合的初态
    （行动菜单、倒下换人、学新招、起名）或战斗结束；JEV 只在选单上决策。自动推进的每一步记进这次宏调用的逐步明细。
