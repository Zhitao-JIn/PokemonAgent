## 二、设计原则

### P-1 可信度判定原则

**LLM 对记忆可信度的判断，不能单独作为采信依据。** 一条记忆要进入"可采信"状态，
至少要通过一项**效果核验**：该记忆被复用时，它声称的效果是否在环境中实际出现。

- **依据**：arXiv 2601.05504 实测，Gemini-2.0-Flash 以满分可信度接受了 82 条候选记忆，
  其中 54 条是恶意的；GPT-4o-mini 走向另一个极端，23 条全部拒绝（平均可信分 0.28）。
  作者结论：这类可信分只是"置信过滤器"，不是"安全过滤器"，建议改用对照不可变真值的效果核验。
- **补充依据**：arXiv 2606.22030 实测，从文本措辞推断可信度时，一句语气肯定的假话可得 0.96；
  按来源定可信度才能挡住批量投毒。
- **落地方式**：证据强度按**来源类型查表**决定，不由 LLM 给数值（见 B1 的来源标签）。

### B0 记忆没有分层时，"谁读、谁写、能否回滚"无法回答

状态：💬 ｜ 叙事：科研 ｜ 归属：项目 1 定义，项目 3 承载 Wiki ｜ 依赖：J1 ｜ 最后核实：2026-10-26

**问题**：现有记忆（act → task → episode → run 四级阶梯、object_fact、人工维护的 knowledge）按检索单元划分，
没有规定哪一层可以进决策 prompt、哪一层可以被改写、哪一层必须不可变。

**证据**：WikiSkill（arXiv 2608.27454）消融显示，在进化过程中让推理 agent 读 Wiki
会降低最终技能质量——"决策侧读什么"必须由分层显式规定。

**方案**：四层 = 一条主链 + 一条旁支。主链 Raw → Wiki → Skill（WikiSkill）；旁支 Raw → 价值记忆（JitRL，B2），不经过 Wiki。

| 层 | 内容 | 写入方 | 读取方 | 可改性 |
|---|---|---|---|---|
| Raw | 发生过什么（事实带来源标签，B1） | harness（每步追加） | 所有下游 | 不可变 |
| 价值记忆 | （状态, 动作, 回报） | harness（局末回填） | 对战等短程 subagent | 可重建 |
| Wiki | 失败模式、有效策略 | 离线维护者 | **只有** Skill 提案者 | 只追加修订，永不回滚 |
| Skill | 程序性指令 | 提案者，经门控 | 所有 subagent（全量注入） | 可回滚 |

**验收**：每一类现有记忆在四层中都有唯一归属；AGENTS.md 分层原则按此改写（I7）。

**非目标**：不引入第五层；不让决策侧读取 Wiki。

**参照**：WikiSkill（arXiv 2608.27454）；JitRL（arXiv 2601.18510）。

### B2 对战等短程离散决策没有利用过往回报

状态：💬 ｜ 叙事：科研 ｜ 归属：项目 1 ｜ 依赖：G2、B6 ｜ 最后核实：2026-10-26

**问题**：动作选择只看当前观测与检索文本，过往同类状态下各动作的实际回报没有进入决策。

**证据**：Opus 4.5 报告记录了对战资源管理失败（回复药使用混乱、不保留 PP、硬仗前不补给）。

**方案**：复现 JitRL。记忆存（状态, 动作, 回报），回报沿轨迹 MC 回填（原机制三）；
推理时检索近邻状态，按回报计算各动作的 advantage，以加法形式修正枚举动作的 logit。
论文证明该修正是 KL 约束策略优化的闭式解。

**验收**：同一对战片段重复运行，对战失败率随重复次数下降；与"不修正 logit"组对照。

**非目标**：不更新模型权重；不用于大地图导航等长程决策（由 C1 负责）。

**参照**：JitRL（arXiv 2601.18510，NUS，2026-01；基准为 WebArena 与 Jericho）。

**前置约束**：装配缺省的决策档（`text`）与 judge 档是 qwen3.8-flash（623，DashScope API），plan 为 deepseek-flash，verify 为 claude-haiku-5-5；都走 API，无法读取 logit，须先有 G2 的本地开源模型档。选键已只输出一个键（220/221）。

### B3 Wiki 条目无法追溯到它依据的 Raw 证据

状态：📋 ｜ 叙事：科研 ｜ 归属：项目 3 ｜ 依赖：B1、J1 ｜ 最后核实：2026-10-26

**问题**：WikiSkill 的 Wiki 层只追加、永不回滚，但它归纳出的规律可能建立在错误的观察之上
（VLM 误读、LLM 摘要失真、judge 误判的成败标签），原设计没有把条目依据的证据及其来源显式记录下来。

**证据**：① WikiSkill 原文**没有**为 Wiki 条目设置可信度分数或支持/反驳计数，
唯一的可信度判断是 Skill 在验证集上的门控；
② `docs/spec/PLAN_wikiskill_reproduction.md` 草案有两处与现状不符：
其一，写入了论文中不存在的"战绩字段、revision＋1、evidence 追加 refute"；
其二，trace 描述仍是 0914 之前的形状（`event_id`、`valid=false`、`events/<run_id>-<id>.json`）。

**方案**：
- 每条 Wiki 条目记录其依据的 Raw 事件（trace 事件 uuid）；
- 维护者按 B1 的来源标签区分**确证**（RAM 读数、机械判定的成败）与**线索**（VLM 感知、LLM 摘要），
  只靠线索支撑的结论在条目里显式注明；
- 订正草案的上述两处；
- 删除原 25②c 对 WeKnora 的参照。

**验收**：任意 Wiki 条目可追溯到 Raw 证据及其来源类型；草案与论文、与现行 trace 形状一致。

**非目标**：不对 Wiki 条目做回滚；Wiki 不进决策 prompt；不给条目打概率。

**参照**：WikiSkill（arXiv 2608.27454，Google，2026-08）。

**现状**：`docs/wikiskill/intent.md`（09-24 起草，草案）从论文重新出发、不继承旧草案的设计决定 D1–D8，并把顺序定为先测评体系（F6）、再复现；spec 与代码均未开始。

### B8 所有情境都用同一种方式调用过往经验

状态：💬 ｜ 叙事：科研 ｜ 归属：项目 1 ｜ 依赖：B6、E2、B4 ｜ 最后核实：2026-10-26

**问题**：三层各自在 perceive 格读记忆。10-17（485–491，brain_scope）起按目标层级重定了范围：task 层读本 task 的全部 ActMemory（不再有步数窗口，487），并看到同局同目标的此前 task 索引；episode 层读本局全部 TaskMemory 详情与同一 run goal 下其他局的一行索引（489）；run 层读本 run 全部局详情与过往 run 的一行索引（490）；规划、拆解、蒸馏与判定的请求带记忆首末帧（488–490）；交互事件按 run 隔离（218），L1 背景按本 run 的 goal 身份隔离（555）。这些除知识检索外仍是每圈固定读取，不区分情境是否见过。知识检索在 episode 层按需（225：本局首圈、场景变化、有 task 未成功才重查），在 run 层每圈检索（490），结果整份交给拆解，并随 `TaskInput` 带到每次选键（223）。

**证据**：
- SkillEvolBench（arXiv 2605.24117，2026-05）：原始轨迹常比由其蒸馏的技能更有效（"有损抽象瓶颈"）；技能库越大，冻结评测表现越差；
- NTU 经验复用研究（arXiv 2604.27003，2026-04）：同一任务分布内原始轨迹占优；跨任务时原始轨迹负迁移（ALFWorld A→B −9.5%），抽象洞察正迁移（＋6.5%）；步级重复检索在分阶段任务上有益、在同质任务上有害。
- WikiSkill 的消融针对的是**进化期**读取 Wiki，不能推出"部署时不应使用原始经验"。

**方案**：按情境相似度选择经验形态。

| 情境 | 使用的经验 |
|---|---|
| 命中 B6 已有簇（见过的地点、谜题、训练师） | 原始经验：step / episode memory 直接检索（原 18 质量分加权保留） |
| 未命中任何簇（新情境） | Skill |
| 短程离散决策（对战） | 价值记忆（B2） |

检索触发由"每一步"改为"情境切换时"（E2 意图变化或进入新簇）。

**验收**：检索命中率、决策实际引用率（需决策输出记录所依据的记忆 id）、
与现行"每步四路检索"对照，比较同片段步数与 token。

**非目标**：不撤销混合检索基础设施（J2）。

**参照**：SkillEvolBench（arXiv 2605.24117）；Experience Reuse in LLM Agents（arXiv 2604.27003）。

**待办**：质量分回写（被召回的 step/episode memory 按新一局成败更新 quality）尚未实现，归入本条。

### E1 所有情境走同一套三层图，没有按情境路由的 subagent

**问题**：0923 起 harness 已重构为 run ⊃ episode ⊃ task 三张同构图，每张 5 格（`perceive → review_and_judge → plan_<层> → act → <层>_done`，187–196），episode 层有真拆解器（`decompose`）派发 task。但导航、对战、菜单、谜题、卡住仍走同一套 task 图，没有按情境区分的 subagent 角色，预算已分层并跨局累计、动作按一次按键或脚本调用计数（455–458）。

**证据**：Opus 4.5 报告中的注意力盲区与固着案例需要干净上下文的重新感知；
Anthropic 多智能体研究系统公开的做法是编排者加并行子 agent，以拆分保护上下文。

**现状补充**：三层感知范围按 L0 / L1 / L2 目标重定（485–491）；plan / decompose 统一为递归规划，三层判定统一为 `achieved` / `continue` / `blocked`（561，见 E4）；编排器与 subagent 角色仍未做。

**验收**：
- 单 agent（现行图）与编排器＋subagent 在同一存档片段上的效果与 token 成本对照；
- 写明退回单 agent 的条件（适用边界）。

**非目标**：subagent 不经 A2A 通信（进程内子图）。

**参照**：Anthropic《How we built our multi-agent research system》（2025-06：多智能体系统 token 用量约为普通对话的 15 倍，内部评测比单 agent Opus 4 高 90.2%；官方建议简单工作流能解决的不上多 agent）。

**规范冲突**：AGENTS.md 第五节已改为三张图各有一个状态载体（200–202）；引入 subagent 时须再改（I7）。

### E8 run 结束后没有 run 级规划器，下一个 run goal 只能由调用方给定

**问题**：一次 run 结束后并不是任务结束，而是应重新规划下一个 run goal。现在 run goal 由调用方一次性传入（评测里就是样本自带的 goal），run 内的 plan 之上没有可规划的一层。

**证据**：`pokemon_agent/harness/run/run_entry.py` 里 run goal 的来源（调用方显式传入，或由初始目标表文字拼出）；2026-10-24 把 run goal 与可编辑目标表分离的修复（633–634）：此前 run goal 与 plan 第 0 行是同一份数据，planner 合法拆解会让评分找不到局。

**方案（占位，待定稿）**：run 结束后由**外层驱动**调用独立的 run 级规划器：
- 入参为 run goal 表、各 run 的 `RunResult` 与 `run_index`；
- 出参与 `RunPlan` 同形（新增、更新、排序），读 run 级结果、粒度比 plan 更细；
- run 图本身不改，由外层驱动调用，并有自己的 trace 账名；
- 占位实现可为直通（返回调用方给定的 run goal）。

run goal 表的行状态与跨 run 持久化（大概率落在 run memory 一层）待定稿时再设计。

**验收**：待定稿。

**非目标**：不进入 run 图内部；不改 `review_and_judge` 的停机语义；本条目不承诺实现时间。

**参照**：`docs/run-goal-split/`（intent、spec、plan）。

**现状**：run goal 由调用方显式传入、plan 初始可为空已落地（633、634）；run 级规划器本身仍只是占位。
