## 1. 粒度定义（改前 / 改后）

| | 今天 | 改后 |
|---|---|---|
| `step` | 一次决策 | **一次小 action（一个键）** |
| 一次决策占用 | 1 step | N steps（链长，`sum(segment.times)`） |
| `decide` 调用 | 每 step 一次 | **每条链一次**（链耗尽/中止才回决策） |
| 视觉感知 | 每 step 一次（就是链尾那次） | **每条链一次**（链尾 + 中止那一步） |
| `StepMemory` 一条 = | 一条链 | **一个键** |
| `ObjectFactEvent` | 只有单键 step 产出 | 每个键都可能产出 |

两条不变量取代今天那条「一次决策 = 一次感知」：

- **一次决策 = 一次决策模型调用 + 一次视觉模型调用 + N 次免费的 RAM 观测。**
- 链内执行**只读 RAM**，因此整条链是**确定的**（同存档 + 同链 → 同一状态序列），
  这条是 §7 里 checkpoint 粒度能停在链首的前提，不只是省钱。

## 2. 循环结构：链内多一层小循环

新增两个 state 字段（都进 checkpoint dump，恢复后接着把链按完）：

```
plan             : ActionFromBrain | None          决策交出的整条链（`thought` 是链级的；论据在段上，见 §4b）
pending_presses  : list[ActionSegmentFromBrain]    展开成"一键一段"的待按队列
```

这两个是**循环状态**（随 checkpoint dump，恢复后接着把链按完），**不是记忆字段**——
`StepMemory` 一律不含链，见 §4。

`think_action` 产出 plan 并把 `sequence` 按 `times` 展开进 `pending_presses`；
`act` 每圈弹队首，**派生一个单键 `ActionFromBrain`**（单段、`times=1`，
`thought` 沿用 plan 的、`rationale` 取自所在段）交给 `execute`。

> 派生而不是新建类型，是为了让 `reflect` / trace / 记忆 / `describe()` 全都
> **不用改结构**——它们只认 `ActionFromBrain`，而它照样是"这一步要做的动作"。
> 链在 state 里是 `plan`，在循环里是队列，在执行处仍是那个小 action。

> **现状指引（2026-09-11）**：下面这段图素描写于本次改动当时；此后 `look` → `record_observation`、`advance_step` → `close_step`、`look_after_action` → `perceive_after_action` + `record_action_result`。当前图见 `pokemon_agent/harness/interface/episode_harness_port.py` 的模块 docstring。

```
START → save_checkpoint → look → judge ─(done)→ 收尾链 → END
          └(否)→ get_action_space → 四路 retrieve → merge_retrieval
                → think_action〔产出 plan + pending_presses〕
                → act〔弹一个键执行〕 → look_after_action
                → detect_stall → advance_step
                → store_step_episode_memory → store_object_semantic_memory
                     ├─(队列非空)→ act                     ← 链内小循环
                     └─(队列空  )→ save_checkpoint          ← 即今天的位置
```

一次决策摊薄的是**决策调用与四路检索**；`detect_stall`/`advance_step`/两个 store
每键各跑一次（`reflect` 是纯组装、不调模型，逐键调它不花钱）。

## 3. 感知策略：逐键 RAM，链尾一次视觉

**链内每一键只做纯 RAM 观测**（place / facing / landmarks / map_id / 四邻 / walk_map），
**不调视觉模型**；链尾那一键与中止那一键做完整视觉感知（同今天）。视觉调用次数
与今天完全相等。

三条理由，按分量排序：

1. **判定层需要的字段里只有一项要钱。** 按键名、按键前脚下与四邻的 landmark
   （warp 表 / sign 表 / 精灵表）、前后坐标与 `map_id`、`facing`（精灵表 +9）
   全部来自 RAM；只有 `dialog_text`（弹没弹对话、说了什么）要视觉模型。
   而链体（多段链的中段）按 `GameTools.execute()` 的现有断言只能是方向键，
   `a` 只允许出现在尾键——**视觉证据放在链尾，正好覆盖唯一需要它的那一键。**
2. **确定性。** 逐键调视觉，链的执行结果就依赖模型返回，`replay`/`checkpoint`
   那条"同存档 + 同动作 → 同一状态"当场失效；中止规则只读 RAM 则位对位确定。
3. **成本。** 逐键视觉会让感知成本 × 链长，而它换来的额外信息只有 `dialog_text`。

**必须一起做的两件事**（否则逐键 RAM 会静默劣化下游）：

- **快照要标明"这一帧没有人看过"。** `scene=None` 不足以表达这件事——它也可能
  只是模型没给出 scene。`StepMemory.Observation` 加 `perceived: bool`；`False` 时
  `render()` 必须**显式写一行**「（本帧未做视觉感知：场景/对话等字段不在）」。
  静默省略会被读成"这些字段没变"，而"没读出"和"没变"是完全不同的两件事
  （同一个理由见 `world/interface/domain/facts.py` 里"光标读不出要明写"那条）。
- **截图要脱离感知。** 今天截图是感知调用的副产品（挂在 `MODEL_CALL` 事件上，
  文件名 = event_id，`_frame_event_ids` 按 `(episode_id, frame_step)` 登记）。
  链内键没有感知 → 没有截图 → `before_frame`/`after_frame` 大面积 `None`，
  `judge`/`verify` 的多模态输入会成片缺图。**改法：把帧挂到 `ACT` 事件上**
  （或新增 `FRAME` 事件），`_frame_event_ids` 的语义与 `_frame_b64()` 完全不变。
  代价是每键一次 PNG 编码 + 一次落盘；换来的是"帧存不存在"不再取决于"有没有人看过它"
  ——**换图不该改帧的可得性。**

## 4. StepMemory 字段改写

| 字段 | 改动 | 说明 |
|---|---|---|
| `action: str` | 语义收窄 | 现在是**一个小 action**（`up`），不再是链。`describe()` 在 `times == 1` 时省掉 `×1` 后缀 |
| `stop: StopReason \| None` | **新增** | 见 §5。记的是"这一键之后为什么没有继续按键"——**本步的结局**，不是链的状态 |
| `rationale` | **粒度下沉** | 从"整条链的论据"变成"**所属段的论据**"（§4b）。字段形状仍是 `list[str]`、非空断言不变——**历史记忆文件不用迁移**，变的是语义 |
| `before` / `after` | 语义不变 | 链内键是 RAM-only 快照（`perceived=False`），链尾/中止键是完整快照 |
| `before_frame` / `after_frame` | 语义不变 | 逐键都有（见 §3 第二条） |
| `step` | 语义不变 | 仍是"本局第几步"，只是现在每键一步 |

**不加**"指向 object 事件的引用字段"——理由见 §6。

### 为什么不加链字段（v2 的核心修订）

v1 曾写 `plan` / `chain_index` / `chain_length`。删掉它们不是省字段，是把 §6 那条原则
**用在自己身上**：跨结构的关系一律靠坐标 join，不把对方的投影内嵌进记录。§6 用它推出
"记忆与事件不互存指针"，同一条原则在这里推出"记忆不内嵌链"。

> 判据一句话：**字段的读者问它的时候，会不会说"这一步"？**
> `stop` 的读者问"这一键之后为什么停了"——是这一步的问题，留。
> `chain_index` 的读者问"这条链长什么样"——不是这一步的问题，去。

三条支撑：

1. **链原文的权威位置在 trace，不在记忆。** `THINK`/`ACT` 事件的 payload 记的就是
   "大脑交出来什么"，天然带链原文与该链占用的 step 区间（§7.8）。记忆里再存一份，
   是同一条事实的第二份拷贝——**两份拷贝就有不一致的可能，而这份拷贝没有消费者**。
2. **冗余的性质不同。** `before`/`after` 的重复是**每条自成一体**
   （取回时不用拼上下文），它们重复的是"这一步看到 / 做了什么"，
   **全部属于这一步**。链是从外部结构复制进来的**投影**：它描述的不是这一步，
   而是"这一步被安排在哪一串里"。前者是自足性，后者是无收益的膨胀
   （§7.6 里 prompt 长度会按链长再乘一遍）。
   （`rationale` 曾是这条论证的漏洞——它当时确实不属于这一步，v2 却把它留下了；
   v3 把它下沉到段处理掉，见 §4b。）
3. **不该给消费者它不该依赖的信息。** 链的执行权在循环的 `pending_presses` 队列里，
   大脑读记忆时**不需要、也不该**知道"这是第几键"——一旦依赖了，将来去掉链概念
   （§7.9：`MAX_TIMES` 只是书写压缩）就成了破坏性改动。

**"链尾正常走完"与"链中途断了"不区分，也不损失什么**：这两件事在**序列**里天然可见
（后面还有没有记录），在 trace 里可 join；而检索时大脑问的是"上次在这个坐标做了什么、
结果如何"，不关心这一键是不是链尾。单键链在新模型里就是"一条链一个键"——
**今天的单键行为原样落进来**。

**如果将来"按链读"真的需要分组键**（§7.6），最小形态是**一个 int**：
`plan_step_start`（这条键所属那次决策的起始 step）。不要因为"迟早要用"就把链原文和
两个派生量一起打进去；在真的需要之前不加。

### §4b 理由（`rationale`）下沉到段

**v2 的漏洞**：v2 把 `rationale` 留在记忆里，说它"属于这一步"。**它不属于**——`rationale`
支持的是**整条链**（"为什么要交出这串动作"），对 `up×4` 里的某一下并不成立。按 v2 自己的
判据（只对整体成立、对单个键不成立 → 不进记忆），链级理由本来就该被处理掉。
**这一问把选择逼到刀刃上：要么把理由的粒度下沉，要么理由从记忆里消失**——不能既留链级
理由、又说链级字段不进记忆。

**下沉到"段"，不是"键"：**

- 键级理由是**自相矛盾**的：`times=4` 这个写法本身就在声明"这 4 下是同一个动作"。
  给这 4 下写 4 条理由，等于承认它们本该拆成 4 段——**要么承认同质（理由就该共享），
  要么承认异质（那当初就不该写 `times=4`）**。
- 段是**一次决策里最小的不可再分意图单元**：一段 = 一个意图 × 连按次数。
  `up×4 -> down×2` 两段的理由可以不同（"往上走到头试撞门" / "没撞到就下来找妈"）。
- **它更贴合 `rationale` 的原设计意图。** `ActionFromBrain` 的 docstring 写着"论据是
  **适用条件**——未来取回这条经验时可以检查它现在还成不成立"。适用条件天然是段级的：
  "地上有药水而我手上没有"支持的是"往右走捡药水"，不是"往右再往上"这个整体计划。
- **成本按段数付，不按键数付**：`up×4 -> down×2` 是 2 条理由而不是 6 条；单段链零增
  （段级理由 == 今天的链级理由）。

**结构改动（链级理由取消，只留段级）：**

| 类型 | 改动 |
|---|---|
| `ActionSegmentFromBrain` | **新增** `rationale: list[str]`（1..`MAX_RATIONALE`，必填） |
| `ActionFromBrain` | **删除** `rationale` 字段；链级的"为什么"由 `thought` 承担（它本来就只进 trace） |
| `Brain._parse` | `_parse_rationale` 从顶层移到每段（段 JSON 里读），错误信息要点明"第几段"；**顶层出现 `rationale` 要报 `ParseFailure`**——不许两个位置都能写 |
| `prompts/calls/decide_action/decide_action.md` | JSON 示例改成段内带 `rationale`；"只写为什么选这个动作"改成"这一段为什么" |
| `StepMemory.rationale` | 形状不变（`list[str]`、非空断言照旧），语义从链级变段级 → **历史记忆文件不用迁移** |

> **形状为什么沿用 `list[str]`、不收窄成 `str`**：`_parse_rationale` 已经容忍模型直接写
> 裸字符串（`isinstance(rationale, str)` 会包成单元素列表），所以"只有一条理由"时写作负担
> 就是零；而收窄成 `str` 要同时改 `StepMemory.rationale` 的形状与 `render()` 里的
> `"；".join(...)`，还会逼历史记忆文件迁移——**能力上限白丢，成本照付**。
> list 的价值在"每条是**独立可判真假**的论据"：分条才能对"第几条不合格"定位，也才能
> 计数校验（`_parse_rationale` 超限报 `ParseFailure` 而不是静默截断）——这些一收窄就没了。
> 真正该动的是 `MAX_RATIONALE`（段级要不要从 3 降到 2 或 1），见下面第 1 条。

**顺带暴露的两个数值问题**（要一起定，别等实现时才发现）：

1. **段数没有上限。** `sequence` 只要求非空，段级理由一变就是"段数 × 条数"。
   要么给段数一个上限，要么给段级论据一个更小的条数上限；否则最坏 8 段 × 3 条。
2. **检索要重标量。** `rationale` 是检索打分用的文本（`render()` 与打分共用同一份），
   粒度变细后匹配信号会变，得小样本重跑一遍看选中率。

至此归属规则**零例外**：

> **对整条链成立、对单个键不成立的 → 住 trace**（`thought`、链原文）。
> **对每一个键都成立的 → 住 `StepMemory`**（按键、该段的论据、结果、`stop`）。

§4 与 §6 是同一条规则的两处应用，§4b 是第三处。

## 5. 中止（`stop`）：分情况

| `stop` | 触发判据（纯 RAM） | 作废范围 |
|---|---|---|
| `None` | 无异常：本步之后要么还有待按的键，要么这一键本来就是最后一个 | —— 继续 |
| `blocked` | **方向键**，且位置与朝向都没变，且朝向本就等于该键方向 | **本段剩余次数** |
| `warp` | `map_id` 变了 | **整条链剩余全部** |
| `episode_over` | 本局终止（步数用尽 / `judge` 判定结束 / 世界结束） | 整条链剩余全部 |
| `scene_shift`（待定） | 遭遇战、对话框开启（**要先确认 RAM 读得到**，见 §8 步骤 0） | 整条链剩余全部 |

判据只有一条：**中止范围只扩到"再做下去会产生它没打算要的动作"为止。**
`blocked` 之后再按只是空按（浪费 tick，便宜），所以只丢掉本段剩余次数，后面几段照按；
`warp` 之后再按是在**一张它没规划过的地图上**产生位移（污染世界状态，贵），
所以整条链作废。

两个必须写进实现的细节：

1. **`blocked` 只对方向键成立。** `a` 不改变位置与朝向，"按了没反应"是它的合法结局
   （对话本来就没弹），不是撞墙。
2. **"位置没变但朝向变了"是转身**，不是 `blocked`，继续按。
   （顺带值得在真机上确认：gen1 里换向那一下到底算不算一次位移——`up×4` 从朝左起步
   是走 4 格还是 3 格。逐键观测会第一次把这件事变成可见的。）

留痕：`stop` 写进那条 `StepMemory`，同时进 trace 的 `ACT` payload。**执行层不许悄悄
改写大脑交出来的链**——这条理由和 `Brain._parse` 那句"收到什么就按什么，这里不改写"
是同一个：大脑下一步的推理建立在自己交出的那条链上，链被截了就必须让它读得到；
`stop` + 落点一起给出，它自己就能推出"在第 3 键撞墙了"。

## 6. StepMemory ↔ ObjectFactEvent 的绑定

**绑定的全部就是坐标三元组 `(run_id, episode_id, step)`**，因为 `step` 现在
= 一次小 action。不需要事件引用 id，不需要在两边互存指针。

三个必须成立的不变量（写成断言/前置条件）：

1. **同一步内先写 StepMemory、后写 ObjectFactEvent。**
2. **两个 store 各自单调**：`_check_step_monotonic` 对 step_memory 与 object_memory
   分别把关，step 逐键递增天然满足（等于容忍崩溃窗口的重复）。
3. **恢复时两边按同一个 `keep_step` 一起截断。** `MemoryTool.void_memory_after(
   episode_id, keep_step)` 已经是这个形状（`_void_kind` 对两类用同一个 `keep_step`）。
   **这才是绑定真正被强制的地方**——任何"只截断一边"的改动都会让两个 store 对不上账。

其余约定：

- **1 step : N events 合法**（一格里同时有门和人时出两条），不需要一一对应。
- `ObjectFactEvent.button` 与 `StepMemory.action` 现在指同一件事，**保留 `button`**：
  记忆记录刻意自成一体（同 before/after 的重复），而且它是 `place.key` 之外
  第二个人可读的核对点。
- **不在 `StepMemory` 里存事件**：语义事件是"世界是什么样"（跨 episode 为真，
  自带作用域），情景记忆是"这次尝试里发生了什么"（有时效）——这个分层是
  `StepMemory` docstring 已经划下的。要交叉看，拿同一坐标查两边。

## 7. 受牵连的既有契约（影响面清单）

| 条目 | 落地情况（2026-09-12） |
|---|---|
| §7.1 `recursion_limit` | **已重算**：`(max_steps - step) × per_press + RECURSION_MARGIN`，`per_press` 分链首/链内两档 |
| §7.2 `max_steps` 语义 | **口径已改（键数），数字先不动**——实测证据与上调触发条件见 §10.2 |
| §7.3 checkpoint 只落链边界 | **已落地**（真机 `check_restore` 自 step 1 恢复跑通，帧账随存档走） |
| §7.4 `JUDGE_HISTORY` | **已换单位**：`JUDGE_CHAIN_HISTORY = 2`（链）+ `JUDGE_HISTORY_KEY_CAP = 8`（键帽） |
| §7.5 `STALL_LIMIT` | **未动**：真机四次 run 都是 3 键短局，撞不到阈值；等长局实测再看 |
| §7.6 按链读 | **已落地**（2026-09-12）——机制与实测见 §11 |
| §7.7 截图改挂 `ACT` | **按另一种做法落地**：挂"产出这一帧的那次感知所在的事件"（开局 `OBSERVE`／之后每一键 `AFTER_ACTION`）。`ACT` 不再写帧，理由见 `CHANGELOG.md`（19） |
| §7.8 `THINK:ACT` 1:N | **已落地**：`THINK` 落链首，`STEP_ADVANCE`/`MEMORY_WRITE`/`OBJECT_NOTE` 逐键各一条 |
| §7.9 `MAX_TIMES` 保留 | **已落地**（它是书写压缩，不是执行粒度） |
| §7.10 `world.step(settle=)` | `settle` **已落地**；**链内等待窗口仍未验证**——见 §10.3 |
| §7.11 `rationale` 下沉到段 | **已落地**（`ActionFromBrain.rationale` 删除，段级 `rationale` 必填） |
| §7.12 段级论据预算 | **已定**：`MAX_SEGMENTS = 4`（段数上限）+ `MAX_RATIONALE = 2`（段级条数上限） |

1. **`recursion_limit = 17 * max_steps + 20`**（`run()`）——每圈节点数变了
   （链内一圈只走 6 个节点），公式要按新结构重算。
2. **`max_steps` 的语义变了**：从"决策轮数"变成"小 action 数"。同一数值下允许的
   折腾量变严（最多 N 个键 vs 今天最多 8N 个键），**任务定义里的 `max_steps`
   要重标定，否则一局跑不完**。顺带的好处：预算改以"游戏里按了多少键"计价，
   比"决策轮数"稳定（不随链长波动）。
3. **checkpoint 建议仍只落链边界**（`save_checkpoint` 节点不动，它本来就在链首）。
   每键一份含模拟器快照，会让存档量 ×链长；而链内执行是纯 RAM 确定的，从链首存档
   重放整条链能逐帧复现，链内不必存。恢复语义不变：`void_memory_after` 把链内那几步的
   记忆归档，重放时重新生成。
4. **`JUDGE_HISTORY = 2`** 从"最近 2 步"变成"最近 2 键"，判定器的时间视野缩水到
   1/链长——判定器"证据可能出现在三步以前那一帧里"的前提被打破，必须重标定
   （按链取，或直接调大）。
5. **`STALL_LIMIT = 5`** 在键粒度下计数更快。`blocked` 早停挡住了原地空按的累积，
   但真机上要看一遍有没有新的误杀。
6. **`retrieve_step_episode_memory` 取的是本局全量**，现在条数 ×链长，直接进
   `think_action` 的 prompt——**这是本方案最大的风险项**
   （对照 `docs/experiences/2026-08-31-audit-77s-input-bloat.md`）。
   缓解有两条：链内键的快照是 RAM-only，渲染天然短；以及**"逐键存、按链读"**——
   给大脑看的时候按链合并成一条（"我按了 up×4→down×2，第 3 键撞墙停了，最后落在
   (5,4)"），正好是它自己决策时的粒度。**分组键从 trace 取**：`THINK`/`ACT` 事件带链
   原文与该链占用的 step 区间，join 键仍是 `(episode_id, step)`——记忆侧一个字段都
   不用加（§4）。**建议这一步与主改动分开落地、单独量 prompt 长度。**
7. **截图落盘改挂 `ACT`**（见 §3）。
8. **trace 的 THINK:ACT 从 1:1 变成 1:N。** THINK 落在链首那一步；
   `STEP_ADVANCE`/`MEMORY_WRITE`/`OBJECT_NOTE` 逐键各一条。统计脚本按新关系读。
9. **`ActionFromBrain` 结构不变**，`MAX_TIMES` 保留——它是"计划里一段连按几次"的
   压缩写法（让模型写 `up×4` 而不是四个段），不是执行粒度。
10. **`world.step()` 需要知道"这一键后面要不要 settle"。** 今天 `AFTER_ACTION_FRAMES`
    （10 秒）是 `step()` 内部无条件执行的，链内键不该等 10 秒。倾向给
    `step(segments, *, settle: bool)`：world 的常量不外泄，harness 只说"按完这键要不要
   等世界自己走完"（比拆出独立的 `settle()` 方法少长一个契约项，`WorldPort` 已有 8 个）。
    另一件要定的事：**链内等待窗口（现为 `WITHIN_ACTION_FRAMES` = 2 秒）够不够读出
    换图后的 `map_id`**——换图有淡入淡出，2 秒是猜的，必须真机验；不够就得给链内
    单独立一个常量。
11. **`rationale` 下沉到段是破坏性契约改动**（§4b）：`ActionFromBrain` 的字段、
    `Brain._parse`、`decide_action.md` 的 JSON 示例三处必须同时改——任何一处漏改都表现为
    "解析全失败并重试"，而且报错信息会指向错误的位置（顶层 vs 段内）。
12. **段级论据的 token 预算**（§4b）：段数 × 条数，而段数现在无上限。和 §7.9 的
    `MAX_TIMES` 一起定。

## 9. 验收

- **成本不变量**：同一个 episode，trace 里 `MODEL_CALL(PERCEPTION)` 条数改前改后
  **必须相等**。这是"逐键不上视觉"唯一的运行时证据，也能自动化。
- **确定性**：同 ROM + 同存档 + 同链 → 同一 `StepMemory` 序列（含 `stop`）。
- **配对**：每个 `(episode_id, step)` 在两个 store 里同时存在或同时不存在；
  `void_memory_after` 跑过之后仍成立。
- **可读性**：trace 里"第 N 键 → 命中哪一格 → 产出哪条事件 → 写进哪条 StepMemory"
  一眼能对上。

## 11. 按链读落地（2026-09-12）：先量后改、机制、以及"那个 int 台阶"的用法

### 11.1 先量（§7.6 要求的"单独量 prompt 长度"）

拿真机产物量的（`trace_data/realcheck-0911-220741` 等四次 run 的 `model_call` 事件里
存着完整 prompt，`memory/step_memory/*.json` 存着记忆本体）：

| 量 | 实测值 |
|---|---|
| 一条 `StepMemory` 渲成文本（`render()`） | **约 490 字符**（9 条样本：462–623） |
| 决策 prompt 本体 | 13.3k → 15.6k 字符（随步数增长） |
| 其中「相关记忆」一节 | 9 → 464 → 971 字符 = **0.1% → 6.8%**（step 0/1/2） |
| 判定 prompt 本体 | 3.7k → 4.0k 字符（小） |
| 判定 prompt 的 history 一节 | 约 250 字符/条 |
| 每次决策实际交出的键数 | **全是 1**（`press_count`，四次 run 全部） |

**读法**：链长 1 时「相关记忆」在 15 步上会占到四成——**这是 0905 就有的老性质，
不是 (14) 引入的**；(14) 引入的是它**按链长线性放大**（链长 4 就是 4 倍，链长 8 就顶穿）。
同时实测的 `press_count` 全是 1，说明今天还没有真实的膨胀——但那是"模型还没用起连按"，
不是"链不会变长"（`repeat_hint.md` 正是主动教它连按的那一段）。

> **补记（2026-09-12，落地后的第一次真机 run `realcheck-0912-062841`）**：
> **上表最后一行过期了——出现了链长 2。** 该局两次决策的 `press_count` 是 2 与 1
> （第一条链占第 0/1 步、第二条落在第 2 步），`plan_step_start` 落盘为 `[0, 0, 2]`。
> 于是「相关记忆」一节在该局第 2 次决策的 prompt（14398 字符）里占 **5.40%**
> ——与上表"随步数增长"的区间同量级，**没有失控**（合并渲染按设计只摆两端两帧）。
> 单次链长 2 不足以触发 §11.2 决定 3 的"平均链长 ≥ 2 就按倍数上调 `max_steps`"
> （四次 run 平均仍是 ~1.2），**但足以说明"链长 > 1 不再只是纸面推断"**，
> 那条触发条件要盯紧了。

### 11.2 三个决定

1. **分组键 = `StepMemory.plan_step_start: int | None`**（§4 预留的台阶，取最小形态）。
   - `None` ⇒ 按 `step` 算，**老记录天然正确**：粒度下沉之前一步就是一次决策，
     两者本来就相等。
   - **为什么不从 trace 取**（v1 当初的想法）：harness 手里只有 trace 的**写口**，
     没有读口；为取一个 step 区间去加一条"harness 读自己的 trace"的契约，比加一个
     int 重得多，而且第 0 步那条链没有 THINK 可查。
   - **为什么不做成 `chain_index`/`chain_length`**：那两个描述的是**链**
     （读者问"这条链长什么样"），`plan_step_start` 回答的是**"这一步是哪次决策按的"**
     ——§4 的判据原样适用。它只被用于分组（渲染与取窗），存储与检索都不依赖它。
2. **合并渲染只给决策者看的那一版**（`render_chains()`）：一次决策一段、只摆两端两帧；
   拿证据的那条路（判定器/校验器）继续用逐条的 `render_sequence()`。**中间帧不是被删掉的**
   ——记忆里一条不缺（"省的是渲染，不是存储"），而且粒度下沉之前它们**从来不存在**
   （一次决策只感知一次）；合并渲染把决策者看到的信息量恢复到那个水平，**多给**的是
   每一键的动作、步号与结局（`stop`）以及每一段的理由。
3. **判定器窗口换单位不换数字**（`JUDGE_CHAIN_HISTORY = 2`）：旧口径"最近 2 步"=
   最近 2 次决策 = 最近 2 条链；另加键帽 `JUDGE_HISTORY_KEY_CAP = 8`，防"链一长
   就静默膨胀"。取窗实现是"按键数上限取回 → `last_chains()` 按链裁"——**不把链砍成
   半截**（半条链上"这一键之后为什么停"读不出来）。
