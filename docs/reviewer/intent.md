# intent —— Reviewer：全链路只读透明的最终裁决席（人与 AI 同权）

> 流程位置：**intent.md** → spec → plan → 落码
> 关联：`docs/reviewer/spec.md`（落地设计）、`pokemon_agent/harness/interface/reviewer.py`、
> `pokemon_agent/harness/reviewing.py`、`docs/workflow.md`
> 本文只写最终意图；信封、线上协议、数值与实施顺序归 spec。

---

## 一、一句话意图

Reviewer 能**只读地看见整条链路**（harness 自己能看到的一切），并对两类节点握有**最终决定权**：
**插话**（对「把目标拆成 task / 规划」的产出）与**审**（对 judge 的「已达成」裁决）。
有决定权，**没有修改权**：只能说「不对，带着这句话重做」，或「认 / 推翻」，不能亲手改任何字段。
**人与 AI 对此完全同权**：同样的视野、同样的两种权力，只是入口不同。

## 二、为什么这样做

1. **决定权与修改权分开。** 让 reviewer 直接改写结构体，会和 LLM 产出重叠成两份事实来源。插话仍由 LLM 带着意见重填，审仍只翻转结论——每个产出永远只有一个作者。
2. **审点收敛到 judge。** 阶段结论的最终裁决只发生在 judge 处，不在每个 task / episode 的结算处另设一道。
3. **透明是裁决的前提。** 握有最终决定权的席位，必须能看到 harness 自己看得到的一切，并能回头翻。
4. **人与 AI 同权。** AI 模式是正式形态，不是降级形态。人和 AI 看到同样的东西、能做同样的事，人才能真正复核 AI 的依据。
5. **只读是唯一的边界。** 透明的限制不是「哪些东西不让看」，而是「任何查询都不能产生写」。
6. **reviewer 是一个独立进程，harness 只依赖端口。** 编排、人席、AI 席与只读读端口同在 reviewer 进程内；harness 只认自己定义的 `Reviewer` 端口（run 侧是一个薄适配器），不知道对面是人、AI 还是脚本。

## 三、范围

| 项 | 取值 |
|---|---|
| 生效层 | 默认 **episode 与 run 两层**；task 层**可选**，由配置 `REVIEW_LAYERS` 开启，默认关闭 |
| 插话落点 | `plan_run` / `plan_episode`——即「把目标拆成 task（decompose）」与规划的产出 |
| 审的落点 | 各生效层的 `review_and_judge`：judge 判「已达成」时亮给 reviewer（开启 task 层后，task 层同样只在这一处审） |
| 不再有的审点 | 两层 `_settle` 里对 task / episode 结算的单独审（收敛到 judge） |
| 席位 | 人（**终端**，reviewer 进程自带）与 AI（Pydantic AI，同一进程），同权；运行模式在启动 reviewer 进程时显式指定：仅 AI / 仅人 / 两者 |

> 术语：「decode」＝ `plan_episode` 里的 decompose（把目标拆成 task）。
> 网页入口暂不做（后续在同一编排模块上加壳）；实时画面展示与 reviewer 无关，从 reviewer 子系统移出并另立项目。

## 四、reviewer 看得到什么（只读）

| 可见面 | 说明 |
|---|---|
| **随问快照** | 产出这次表单 / 裁决的那封大脑请求原样（＝「大脑看到的」）、目标表或任务表、计数。请求里的记忆对象带着大脑这一问看到的图；提问时刻的当前画面不随问带，按需取 |
| **trace** | 默认本 run，可指定其他 run；可按局 / task / 来源 / 账名过滤，从最新往回翻 |
| **记忆** | 统一召回，跨 run 共享，与大脑召回同一批 |
| **历史画面** | 指定某局某步的按键前 / 后画面 |
| **往期问答** | 本次 run 内 reviewer 已处理过的问与答 |

reviewer 自己持有 trace 与记忆的只读读端口，由人或 AI **按需拉取**，不预先推送；RAM 现状已在快照的请求里。

**同一套查询、两个入口**：人在终端里敲命令，AI 用工具调用；两者发出的是**同一个查询类型**，结果文本同一份口径。
命令行语法只是类型化接口上的一层薄翻译，不含业务。

## 五、reviewer 做得了什么

| 能力 | 人（终端） | AI |
|---|---|---|
| 插话（让 LLM 带着这句话重做） | ✅ | ✅ |
| 审（认 / 推翻，推翻必附理由） | ✅ | ✅ |
| 看快照、查全链路 | ✅ | ✅ |
| 改写任何字段 | ❌ | ❌ |

唯一的非对称是 AI 的两道**安全阀**，它们是对无人值守模型的成本与收敛保护，不是权力差别：
每问最多若干次查询、总时限；连续生效的插话最多若干轮（人的意见永远生效，且清零计数）。数值是实验旋钮。

## 六、AI 席的形态

- 是 reviewer 进程内的一个模块（asyncio 任务）；包边界禁止引用 brain 与 harness 实现；Pydantic AI 依赖只进 reviewer 进程。
- 从「一次视觉 LLM 调用」升级为**带只读工具的有界对话**：用模型原生的工具调用（function calling）查证，再以一次「提交结论」的调用作答；工具参数的 schema 直接复用查询模型。
- 复核者而非第二个 judge：审的是「judge 的结论与它自己摆出的证据是否一致」，不是重新判一遍目标成没成。
- 失败零后果：提案缺失 / 超时 / 解析耗尽 = 没人答，run 继续。
- **仅 AI 模式**：reviewer 进程无终端（headless）、不倒计时，提案立即生效；AI 失败则记为没人答。
- **人 + AI 模式**：AI 出提案后启动倒计时，人在期间可接管；倒计时归零则自动提交 AI 提案。

## 七、核心原则（落码时的判据）

1. **只读视图不得成为写通道。** 由窄接口（只暴露读方法）在类型上保证。
2. **产出只有一个作者。** reviewer 影响产出只能经「重问」。
3. **没人答 = 认账 / 无意见**（既有语义不变）。
4. **每次问都记一笔账**，并记清**谁答的**（人 / AI / 没人）、是否被轮次阀截断。
5. **harness 知道「谁答的」标签，不知道对面是什么实现。** 两个方法的签名承诺不变。
6. **查询由 reviewer 自己读共享存储回答。** trace 与记忆的真源是共享存储，reviewer 持有只读读端口；harness 每次提问前先 flush trace，保证读到最新账。
7. **插话循环必须收敛。** 对 AI 的连续插话设轮次安全阀，到顶接受当前版并留痕。
8. **同一信息不两处传，schema 复用。** 查询模型一份，命令与工具 schema 由它派生。
9. **reviewer 的画面只来自随问快照里的记忆对象与只读历史读取**，与实时流无关。
10. **类型化 API 是契约，命令行是翻译壳。** 每条命令须有「等价于某个类型化调用」的测试。

## 八、明确不做

- 改写权（reviewer 直接替换结构体 / 表 / state）。
- task 层的插话（逐步 `choose` 处插话）：task 层最多 12 步，逐步插话会让 run 被反复阻塞；task 层只提供 judge 处的审，且默认关闭。
- 对 judge 判「没达成」或机械停机的审（维持现状）。
- 网页前端、鉴权、历史 run 的回放、多个 run 同时共用一个 reviewer 进程、多终端同连。
- 「最近历史摘要」自动附带（reviewer 要看历史自己查）。
- 自治 agent：AI 席不自停、不自决、不碰写。
- 用 A2A 或 MCP 作为 harness 与 reviewer 的边界（理由见 spec §十七；保留将来给 hub 包 MCP 薄壳的可能）。

## 九、死代码清理（意图的一部分）

- 实时流相关：`LiveFeedTrace`、`live_feed_url`、Feed 信封。
- 线上陈旧字段、过期 docstring、对应测试与文档。

**范围判据**：只清「本次意图使之失效」与已核实的陈旧项，不扩大到无关的历史遗留；每项先查读方、读方清零才删；清理与引起它的那步同提交。

## 十、需在 spec / plan 阶段落实的前提

1. **图片 + 工具调用能否在同一请求里使用**（所选视觉模型）——先用探针验证；不通过则分级降级。
2. **历史画面是否有纯读路径**——不满足的项不上线，不用有副作用的路径凑数；记忆侧没有按步取帧的现成接口，需先核实经 `recall` 取帧是否可行。
3. **trace 跨进程可见性**：run 进程提问前 flush，另一个进程能否立即读到最新账；`TraceToolPort` 有没有 flush 接口。
4. **规范改动需你确认**：`CLAUDE.md` / `AGENTS.md` §四第 3 条「人审推翻只改目标表 / 任务表（`overturned`），定案以表为准」，随推翻只剩 judge 一处且只写 `last_judge` 而失效。

## 十一、验收（机械可验）

1. 审只出现在 `review_and_judge`：默认两层；`REVIEW_LAYERS` 含 `task` 时再加 task 层。各层 `_settle` 不再调用 reviewer；默认配置下 task 层不调用 reviewer，行为与改动前逐位相同。
2. 人（终端）与 AI 可用的查询集合由**同一个类型**定义，两处入口没有私有查询类型。
3. 任何查询前后，trace 与记忆的内容都不变；reviewer 进程里不构造 game / brain 端口。
4. AI 的插话重问在轮次安全阀处终止，账里能区分「AI 被截断」与「AI 没意见」；人在中途接管后计数清零。
5. 回话带有「谁答的」标签，且与「是否真的有人答」恒一致。
6. harness 只依赖 `Reviewer` 端口；`reviewer` 包（装配入口除外）不 import harness 实现、brain、world。
7. 死代码清单逐项清除，仓库内对应符号零残留。
