## 一、一句话意图

**检索的每一次执行都自带账（耗时分段、语料、确定性序号），每一次变更都对着工业 rubric 有据可依——
库从 12 条长到千条的路上，没有任何一段延迟、任何一个 bug 是靠猜定位的。**

## 二、为什么现在做

1. **延迟是黑盒。** 真机 run 的 `query_knowledge` 单次 2~9 秒波动（对照：全链路 LLM 调用均值 0.99~3.24s），
   而 trace 里只有一笔总账——回答不了"时间花在哪"。主嫌疑（rerank 段 15 条候选无截断全量过
   cross-encoder）只是推断，没有分段账之前一切优化都是盲调。
2. **sidecar 在病理膨胀。** `knowledge_memory/vectors.jsonl` 697 行只对 12 条记录（7.7MB），
   98% 是垃圾行；且每次进程重启后的首次检索都会再追加一轮。
3. **工业差距评估给出明确短板分布。** 对照腾讯云五层架构 / 美团三级指标体系 / 蚂蚁意图前置 +
   百炼 Agentic RAG 建 17 维 rubric：骨架（BM25+向量+RRF+cross-encoder）达标，塌的是
   **运营层（零评估、零归因）与效率层（无压实、无缓存、无持久化）**——大规模基建（ANN/量化/GPU）
   离当前规模差几个数量级，是伪差距。
4. **聚合的基建已经有主了。** 真机观测走 langfuse（`read_knowledge` 是 retriever 型 span），
   自研聚合面板没有位置——检索侧要做的是**把账记对记全**，聚合交给 langfuse。

## 三、三笔变更与各自的意图

| 主账 | 一句话 | 关键决策（与被否掉的方案） |
|---|---|---|
| **324** | 检索分段耗时**随返回值出**，`read_knowledge` 账 content 带 `timings` | 对齐 provider `complete()` 返回带 usage 的先例：观测数据是产出的一部分。**否掉了 timings_sink 回调旁路**（多一层间接只为绕开"污染返回值"这个不成立的顾虑）；也**不加"每段一个文件"**——同刻决胜与排序是另一条线 |
| **325** | trace 封套加 `seq`：同刻 `ended_at` 的决胜键归 trace 自己递增 | node_io 概率性挂（同环境两次 run_fake 两种账流）暴露：决胜键 uuid 是**随机的**，同刻账每次进程随机洗牌。用户拍板三连：加 seq / 不是 tool 层代管（"我在用 langfuse"）/ 重启置零不持久化。**旧账不做兼容**——缺 seq 解析失败被扫盘跳过，即"删了" |
| **328** | RAG-2 收尾 + BM25 语料持久化 | hash 判编辑（mtime 只配当预筛）、sidecar 压实（697→12 行）、corpus 随 index.json 持久化 + 索引本体按语料指纹缓存。**写批处理（L1-04）按用户指令不做** |

三笔的公共哲学：**每一级缓存/账本的失效都靠"数据指纹自然失配"，不维护显式失效清单**——
BM25 指纹是 sorted texts 元组、corpus 是内容本身、seq 是 append 序；数据变了它们自然不再成立。

## 四、关键设计定案（含"为什么不是那个"）

1. **timings 只在 `read_knowledge` 有，五条等值读口没有。** 等值过滤单段、微秒级，
   `{"filter": ended_at - started_at}` 精确等于双时刻差——零信息增量的副本（node_io 删 `count`
   的同一条判据）。整段时长六条读口早就有（双时刻定案）。
2. **BM25Okapi 不 pickle，持久化的只有分词 corpus。** pickle 耦合 rank_bm25 库版本——
   "升级一个库"不能变成"账本读不出来"。token 列表是纯 JSON，任何版本可重建。
3. **index.json 全量重写，不做分段文件。** 任何一段失效都五段重写——换来"段间永远一致"
   （一次原子 rename，要么全新要么全旧）与"派生物 + 对账自愈"的既有语义；拆段文件引入
   N 份派生物互相打架的新崩溃窗口，收益是省几 KB 写入。跨进程覆盖由"记录文件是唯一真相 +
   启动对账自愈"兜底，生产外另有"一次只跑一个"红线。
4. **BM25 语料指纹用 sorted texts 元组直接比较，不用 hash。** 候选顺序来自 set 交集
   （每次进程可能不同），sorted 保证稳定命中；BM25 打分对语料顺序不敏感，顺序漂移只影响
   命中率不影响正确性。内容一变指纹自然失配——失效零钩子。
5. **`rank()` 的 `self._vectors or {}` 是 697 行的主凶**（324 顺带修）：惰性加载被短路，
   每次重启后首次检索全量 miss → 全量现算 → 全量 append。58 次启动 × 12 行 ≈ 697 的来历对上了；
   git mtime 误判只是帮凶。教训入档：**"缓存 dict 判空"和"惰性加载判空"长一样，但前者不触发加载。**

## 五、明确不做的（与理由）

- **金标评估集**：跑分基建与样本起草可全自动，但"这条 query 应命中哪条记忆"的真值必须用户背书
  ——AI 自判是循环论证。样本表起草后等用户半小时勾选。
- **RAG-3 精排截断**：等 324 的真机分段账证实 rerank 占比后再动，且需要金标集守住召回
  ——改动前基线都没建，动它就是盲调。
- **写入批处理（L1-04）**：写入频率低（每键一条），12 条规模收益几十毫秒，用户指令明确不做。
- **ANN / 量化 / GPU / 多租户 / chunking**：规模不适用——收益阈值离 12 条差几个数量级。
- **自研聚合面板**：langfuse 已在承担，检索侧只保证 content 账全
  （契约测试 `test_query_knowledge_returns_per_stage_timings` 钉住五段齐全）。
