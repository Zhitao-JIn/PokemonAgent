# 工程经验文档体系与未来目标（EXPERIENCE_DOCS）

> 本文件是"经验文档 + 可观测/可审计/测评"的**定稿方案**，回答三个问题：
> **去哪**（未来目标路线图）、**怎么记**（经验文档设计）、**怎么算成**（验收标准）。
> 2026-09-01 定稿。

## 一、背景与立场

项目所有改动目前只落在 CHANGELOG（"改了什么"），缺"**为什么、怎么定位的、验证了什么**"。
而最近两天的每一个问题——审计 77 秒、`KeyError` 跨 run 泄漏、权限漏配静默降级、run 无限跑、
agent 连续无效动作——**都是只有真实 run + 翻 trace 才能发现的**。这说明两件事：

1. **可观测是这个项目唯一的调试手段**（没有它，任何改动都在黑箱里做）；
2. **分析路径本身是资产**——"怎么从 trace 读出一个 bug"的方法论，比 bug 修复更值钱。

立场（定稿，不再摇摆）：**经验文档即使过时也是资产**。它记录的是"当时那个系统状态下
的分析路径"，和复现案例是同一种东西——过时不代表无用，它证明的是"那段时间发生了什么、
怎么诊断的"，未来的同类问题可以直接复用路径，而不是从零开始。

## 二、两类文档的分工

| | 活文档（Living Docs） | 经验文档（Experience Docs） |
|---|---|---|
| 内容 | 当前状态：架构/接口/契约/数据流 | 一次问题的分析→定位→解决→验证 |
| 时效 | **怕过时**——跟随代码更新 | **过时没关系**——历史资产 |
| 位置 | `docs/spec/`（各模块 SPEC） | `docs/experiences/` |
| 更新者 | 改代码的人顺手改 | 问题解决后写一篇 |
| 例子 | `docs/spec/DATAFLOW.md` | `docs/experiments/0827-false-positive-analysis.md` |

**判断标准**：写下来的东西属于哪一类，看"它三个月后还准不准"——还准 = 活文档，
会过时但记录了当时的分析 = 经验文档。**两类都要，不互相替代。**

## 三、经验文档模板（四段式）

每篇经验文档固定四段，头部带元信息。模板：

```markdown
# <一句话问题描述>

- 日期：YYYY-MM-DD
- 关联 Issue：`#NN`（GitHub issue 编号，可空）
- 关联 commit：`<hash>`（可空）
- 系统状态：当时的代码大致状态（如"观测台首跑、max_steps 默认 50、全局限速前"）
  ——**记录"当时"，过时没关系**，这是给未来读者定位历史上下文的锚点

## 一、分析（现象）

现象是什么、在哪观测到的（trace 事件 / 观测台 / 日志）、影响面。
**附上可复现的证据**：trace 片段、日志行、实测数字（token/延迟/事件数）。

## 二、定位（调查路径）

看了什么（文件/事件）、测了什么（命令/脚本）、证据链怎么一步步收敛。
**这一步是全篇最值钱的部分**——未来的同类问题照这个路径走。

## 三、解决（改动与取舍）

改了什么（文件）、为什么这么改、**取舍**（选了 A 没选 B 的理由）。
保留"改错了再纠正"的记录——那也是经验（如"tick(60) 单次调用测限速，结论错了，
逐帧 tick(1) 才是对的"）。

## 四、验证（测试变化）

测试变化（新增/修改用例、数量、是否全绿）、端到端确认（真实 run 的证据）、
遗留问题（未解决的部分，链到下一个 issue）。
```

**轻量原则**：不追求完美排版，追求"路径可复现"——文档里出现的分析脚本/命令
必须能重跑。写一篇的经验是"分析"占 60% 篇幅，"解决"占 30%，"验证"占 10%。

## 四、存放、命名与关联

- 目录：`docs/experiences/`（新建；`docs/experiments/` 留给"每批实验数据的分析"，
  与单问题经验文档分开——语义不同，前者是批次统计，后者是单点诊断）。
- 命名：`YYYY-MM-DD-短横线主题.md`（如 `2026-09-01-run-level-guardrail.md`）。
- 索引：`docs/experiences/README.md` 登记每一篇（一句话摘要 + 链接），
  新文档必须登记——**没有索引的经验文档等于没写**。
- 与 issue 关联：经验文档头部写 `关联 Issue`；issue 解决后，回复里贴文档链接，
  双向可查。

## 五、流程（何时写）

1. 解决一个**端到端问题**（真实 run 才暴露的 bug / 行为问题 / 性能问题）→ 写一篇；
2. 纯代码内部重构（无新问题）→ 不写，CHANGELOG 足够；
3. 写的时间：问题解决后**当轮收尾**（和 CHANGELOG、memory 一起），不攒；
4. 一篇的篇幅：500-1500 字，模板四段，不写流水账。

## 七、验收标准

1. 每个端到端问题解决后，24 小时内有一篇 `docs/experiences/` 文档并登记索引；
2. 文档可复现：分析脚本/命令原样能重跑，证据链完整；
3. 三个月后回看：新成员（或未来的自己）凭文档能定位同类问题，无需翻代码史；
4. 路线图 P0-P3 每期完成时有对应的可量化产出（护栏触发次数、token 聚合视图、
   判定器失效率、成功率报表）。
