# intent —— 两层递归规划：状态表、验收条件与执行闭环

> 流程位置：**intent.md（修订草案，供审阅）** → spec → plan → 落码。
> 关联：`docs/brain_scope/intent.md`、`docs/spec/evals/SPEC.md`、
> `pokemon_agent/brain/interface/domain/{run_plan,decomposition}.py`。
> 本文规定机制与行为；具体字段、身份编码、图路由和迁移归 spec。
> 本次只修订意图，生产接口、状态模型及冻结 dataset 均未修改。

## 一、一句话意图

plan 与 decompose 使用同一套递归规划机制：围绕当前父目标及其验收条件，
维护直属子目标状态表，提出新增、保留、重开、放弃与后续执行方案。
两层产出的每个子目标都包含可核验的成功条件和有明确单位的预算；
由 harness 派发、judge 判定、harness 结算回表，再交给本层规划器修订。

## 二、两层对应关系

| 机制 | plan，服务 L0 | decompose，服务 L1 |
|---|---|---|
| 当前父目标 | run 的总目标 | 当前 L1 goal |
| 维护的直属子目标表 | L1 goal 表 | L2 task 表 |
| 子目标内容 | 目标、验收条件、预算 | 目标、验收条件、预算 |
| 表项操作 | 新增、保留、重开、放弃 | 新增、保留、重开、放弃 |
| 一次派发 | 一次 episode 执行 | 一次 task 执行 |
| 结果回写 | 判定与结算后更新 L1 表项 | 判定与结算后更新 L2 表项 |

相同的是规划和回表机制；层级、执行单元与预算单位仍各自明确。
plan 子目标的预算限制下派 task 的规模，decompose 子目标的预算限制动作规模，不能混用。
同构不要求模块两侧共用一个 Python 类，仍遵守现有方言与门面转换边界。

## 三、现状与差距

1. plan 新增目标已经具有 `goal`、`success_criteria`、`max_steps`。
   验收条件不是本次新发明的字段，需要在两层契约和 prompt 中明确保持对齐。
2. episode 现在已有 TaskEntry 状态表，decompose 的请求也能读到它。
   差距是 decompose 当前只返回新任务链，不能像 plan 一样定点维护已有表项。
3. 当前 task 只派发一次；失败后重拆为新条目。目标身份和执行身份尚未像 L1 goal/episode 那样分开。
4. 当前 plan 无 pending 时 fail-fast、decompose 强制非空，不能完整表达无合法后续的现场。
5. 本次优先统一状态表与验收闭环；受阻/复核表达作为该闭环的配套出口。

## 四、规划输入与输出意图

- 两层都明确接收本层父目标及验收条件、直属子目标表、该层既定可见范围内的记忆、当前观测、反馈和预算。
  plan 当前父目标与验收条件的传递需要在 spec 中核对并补齐，不能只依赖含糊的目标表推测总目标。
- 两层输出在概念上同构：新增子目标、对已有表项的修订、规划理由，以及当前是否有可采纳方案。
- 已有条目未被点名就保留；不要求重写整张表，不因重规划自动丢弃全部剩余任务。
- 两层都可以显式重开失败条目或放弃已不适用的条目；新前置条件与后续任务必须具有正确执行顺序。
- 不再把 decompose 定义成只能追加一条新任务链。触发重规划时，已有 pending 条目也属于可审视和修订的对象。
- 具体字段名在 spec 中统一确定。上一版仅将 plan 的 `updates` 改成 `goal_updates` 的决定撤回，
  应同时考虑两层对各自子目标表的相同操作，不分别固化两套含义相同的命名。
- 子目标目标内容、验收条件或预算发生实质变化时，以有来源的新条目替代并保留旧条目历史，
  不在同一身份上悄悄改写“当初要完成什么”。是否需要显式排序/前置关系，归 spec 确定。

## 五、状态表、身份与事实归属

1. 每个逻辑子目标有稳定身份，表项可追踪状态、尝试次数、最近执行引用、修订理由与既有 review 定案信息。
   两层保持这些字段的同等语义，具体执行引用类型与版次字段可体现层级差异。
2. 任务表新增重开能力后，同一 L2 目标可有多次执行；每次执行必须具有独立身份。
   不能直接复用原 task 执行 ID，把新旧 ActMemory、TaskMemory、trace 和预算账拼成一次执行。
3. 表项身份用于“重开哪个逻辑目标”，执行身份用于“这一轮发生了什么”，二者必须分开。
   既有 L1 goal 与 episode 的分离是参照，不用目标文本代替新执行的唯一身份。
4. 两层规划器都只提出主观修订；completed/failed 仍由 judge 与 harness 按现有执行结算职责产生。
   重开不删除过去的成功/失败记录，放弃也不抹除已经发生的尝试。
5. 已完成条目默认保留；确需重做须给出依据并经过既有 review 采纳，不能无理由重复派发。
6. 状态表是当前定案来源；历史记忆仍保留各次执行的来源章，不从蒸馏正文反推结果。
7. 不擅自修改既有 brain scope。详情按当前执行单元隔离，背景继续按已确认范围提供；
   新逻辑任务身份如何与现有同目标背景索引衔接，spec 必须说明，不顺带改变检索范围。

## 六、验收条件闭环

- plan 的每个 L1 goal 与 decompose 的每个 L2 task 都必须带明确、可由执行材料核验的验收条件。
- 目标描述回答“做什么”，验收条件回答“看到什么证据才算达成”，预算回答“本次最多执行多少”。
- 上层验收条件约束下层拆分，但上层成功不能简单等同于某一个下层任务完成或所有表项都无待办。
- 每次子单元执行后，先按该子目标的判据判定与结算，再更新本层子目标表；
  本层父目标是否达成，继续由对应 judge 使用父目标判据判断。
- 修改表项状态不能代替环境证据；规划理由不能代替判定，任务表清空也不能直接表示成功。

## 七、无合法方案与复核出口

两层都允许表达“当前有提案”“暂时无法提出合法方案”“需要复核父目标是否已满足”。
具体类别与载荷约束归 spec，不在本 intent 固定枚举。

- 无提案时不强制编造目标或 task；不能同时声称无方案又夹带待执行内容。
- 有证据支持的有限探索和纠偏仍是提案，不能因为不保证成功就报告受阻。
- 当前无 pending 是可处理的调度状态，经过判定/复核后决定重规划、交上层或结束当前单元；
  不把“无工作”一律当程序错误，也不能把它当作成功。
- 只有具备合法待办工作才能进入 act；执行入口的前置条件仍受保护。
- 受阻是本次规划意见，不等于永久不可完成或直接失败标签；请求复核不能自行盖完成章。
- harness 明确处理受阻与复核出口，并服从既有重规划、review 和预算上限，禁止空转。
- 解析失败、提供者错误与预算耗尽保留原错误语义，不统一伪装成“受阻”。

## 八、例子

L1 表里已有“治疗队伍”，一次 episode 失败后，plan 可保留此条目并重开，
新的 episode 使用独立执行身份。

该 episode 的 L2 表里已有“到达柜台前”“与护士互动”“确认治疗完成”。
若第一项站位错误，decompose 可以放弃错误条目、保留仍适用的后续条目并补充合法前置任务；
若某个原 L2 目标仍适用但执行失败，也可以重开同一逻辑条目，以新的 task 执行身份重试。
两种选择都需要给出依据，且安排出的执行顺序必须满足前置条件。

每个 L1/L2 条目各带自己的验收条件。改为 pending 不代表已完成，
“护士对话已出现”也不能替代“治疗完成”的上层验收条件。

## 九、评测、留痕与验收

1. plan/decompose 的 dataset 都能表达父目标、子目标状态表与历史尝试引用，包含新增、保留、重开、放弃及受阻现场。
2. solver 继续走生产 Port，不把参考方案交给被测模型；scorer 按结果类别验证结构与合法表操作。
3. AI 质量分评价验收条件、历史使用、重规划和依赖顺序是否合理；建议拆分与表操作不构成唯一白名单。
4. 表修订、采纳、派发、各次执行判定及回表均可追溯；无动作或重开也不能缺账。
5. 集成测试证明两层都能在失败后维护原条目并产生新的执行，旧尝试的记忆、trace 与预算不被覆盖或混读。
6. 完成章仍来自既有 judge/harness 链；两层无方案都有正常、有界出口。
7. 新契约和评测发布新版本，不改写旧冻结 dataset、标注和评测日志。

## 十、范围与下一阶段

保持 plan/decompose 两个调用入口和层级职责；不将 choose 改成另一个状态表规划器，
不增加 choose 的推理字段或停机权，不改变已确认的可见范围，不新增持有状态的大脑角色。

这是状态表与执行身份的机制修改，范围大于单纯输出改名。
spec 必须落实：两层接口形状、表项及尝试身份、定点修订与采纳原子性、顺序与依赖、
重开后的预算与记忆归属、父目标/验收条件传递、图路由、结算与终止类别、review/trace 展示。

因此需要重新核对请求 dataset、状态模型与 checkpoint 指纹的影响，不能沿用“只改输出”的迁移假设。
可复用的旧现场保留来源并通过新版本适配；缺失新语义的用例另行补采。
模拟器存档是否重打、二十场景是否需要重新执行，在 spec/plan 根据实际影响列明；
本 intent 不直接启动打包、采集或实现。
