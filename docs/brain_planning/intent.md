# intent —— 分层规划职责与无可执行方案的出口

> 流程位置：**intent.md（草案，供审阅）** → spec → plan → 落码。
> 关联：`docs/brain_scope/intent.md`、`docs/spec/evals/SPEC.md`、
> `pokemon_agent/brain/interface/domain/{run_plan,decomposition}.py`。
> 本文规定职责、行为与验收意图；具体结果枚举、字段约束、图路由和迁移方式归 spec。
> 本次仅形成修改意图，不表示接口或实现已经变更。

## 一、一句话意图

保留 plan 维护 L1 目标表、decompose 拆解当前 L1 目标的职责差异，统一两者对规划结果的表达：
能给出提案、当前无法给出提案、需要复核目标是否已满足。
由 harness 消费这些结果决定后续调度；不再要求大脑为了满足非空约束而编造目标或任务。

## 二、为什么修改

1. `plan` 容易被理解为普通步骤拆分，`updates` 也没有说明更新的是目标表。
2. 当前 plan 应用更新后没有 pending 目标会抛 `NoGoalToDispatch`。
   这把“当前没有可派发工作”与“不该出现的程序违约”绑定在了一起。
3. 当前 decompose 强制返回至少一个 task。前提冲突时，无法合法表达“现在无任务可执行”。
4. 不能让 planner 为了解决这些限制代替 judge 宣告完成，也不能以“受阻”为理由绕过原目标限制。
5. 评测已经允许等价方案和失败纠偏，生产契约也需要能够表达合理的无方案意见。

## 三、保持不同的主体职责

| 调用 | 职责 | 提案内容 |
|---|---|---|
| plan，服务 L0 | 维护 run 的 L1 目标表 | 新增目标、重开或放弃已有目标 |
| decompose，服务 L1 | 将当前 L1 目标拆成后续 L2 tasks | 从当前现场继续的任务链及必要前置关系 |

- 保留 `plan`、`decompose` 方法名，在接口、prompt 与文档中写清其层级和职责。
- plan 的 `updates` 更名为 `goal_updates`，明确这是目标表修订；按本次输入表的序号定位。
- 保留 plan 的 `push_goals` 和 decompose 的任务链，各自描述自己拥有的对象，不为外观一致合并成泛化列表。
- 保留 `why` 作为规划理由。它可以解释前提冲突、重试依据和复核请求，不能代替事实证据。
- 已有目标的主观修订仍只表达重开或放弃；completed/failed 继续由 harness 按执行与判定结算写入。

## 四、统一外围结果语义

以下是概念类别，不在 intent 中固定代码枚举名称。

| 类别 | 大脑表达什么 | harness 如何消费 |
|---|---|---|
| 有可采纳提案 | 当前有目标表修订或后续任务可提出 | 校验、经过既有 review 采纳，再应用；只有具备可派发工作时才进入执行 |
| 当前受阻 | 根据当前输入，暂时无法提出合法、合理的后续 | 保留理由与现场，进入既有复核、上层处理或有界重规划流程，不执行虚构任务 |
| 请求目标复核 | 当前证据提示目标可能已满足，应先判断是否还需继续 | 返回对应层的 judge/review 流程；由原判定与结算链决定是否完成 |

- 非提案结果无需附带虚构的目标或 task，不允许同时声明无方案又夹带待执行内容。
- decompose 只有在提出任务链时才要求非空；其他结果不能被当成解析失败。
- plan 没有新增目标是合法情况，已有有效 pending 目标可继续使用。
- plan 也可能提出合法的目标表修订，但应用后没有 pending 目标。
  此时不得直接派发，也不因为“没有工作”本身抛程序违约；回到判定/复核链处理。
- “当前受阻”仅是本次规划能力与输入条件下的意见，不等于目标永远不可完成，也不是自动失败标签。
- 不能因为一个动作无法保证成功就报告受阻。有证据支持的有限探索或纠偏仍可作为提案。

## 五、职责与控制边界

1. **大脑提出，harness 调度，judge 判定。** 规划结果不会直接盖完成章或直接停止 run。
2. “请求复核”不得成为自行宣布 goal_done 的别名。judge 判未完成时，也不能无预算限制地重复同一规划调用。
3. harness 必须为受阻和请求复核安排明确出口；不得原样立即重问形成空转。
   重规划、review 与上层交接继续服从既有预算；耗尽时显式返回原因。
4. 没有 pending 是一个可处理的调度状态；强行进入 act 时没有可派发工作，仍然是契约违约。
   不能通过删除执行入口约束来掩盖错误路由。
5. 非法输出、接口解析失败、提供者错误与预算耗尽继续保留各自错误路径；不得统统翻译为“受阻”。
6. 不改变现有 brain scope，不补看未来记录，不从其他 run 或 L1 借入该调用不可见的证据或限制。
7. 沿用现有 LangGraph、review/judge 与结算架构，不新增持有状态的 planner 或另一套停机判定器。

## 六、典型行为

| 现场 | 期望行为 |
|---|---|
| 上一局治疗失败，但当前有其他合法交互位置可调查 | plan 可重开目标，decompose 可给纠偏任务；不因一次失败就宣告不可完成 |
| task 的目标坐标是墙格，但交互意图可通过合法站位继续 | 允许纠正失效前提，提出合理调查或交互任务，而不是重复穿墙或机械报告受阻 |
| 已经逃跑，原目标明确禁止重新遇敌，却要求继续原战斗菜单导航 | 报告前提冲突；不编造重新遇敌步骤，不要求非空任务链 |
| 当前观测提示目标可能已满足 | 请求对应 judge 复核，不再次制造工作，不直接修改 completed |
| plan 合法放弃当前无从继续的目标，更新后没有 pending | 应用经采纳的修订后进入复核，不抛“必须编出一个目标”的异常，不直接 act |
| judge 复核后仍未完成，规划条件也没有变化 | 有界升级处理或返回受阻；不在两个模型节点之间无限往返 |

所有行为只依据该次调用实际可见的材料。建议路线不是唯一方案，未被证明的机制不能写成已知事实。

## 七、评测与留痕

- choose、plan、decompose、judge 仍为四个独立 Inspect 任务；本次不合并评测。
- plan/decompose 的结构评分按结果类别检查：提案核验载荷与预算；非提案核验类别、理由和载荷一致性。
  无需执行的结果不能因为缺少 task 或 pending 而一律判结构错误。
- 质量评分继续使用建议式参考，评价提案是否合理、受阻是否有依据、是否应先复核，以及是否遵守当前目标边界。
- “受阻”不是规避评分的免费出口；明明存在合理下一步却不给方案，应在语义质量中扣分。
- 原先因必须非空而排除的 decompose 冲突现场，在新版本中用于评价受阻表达。
- 模型调用、非提案结果、review/judge 路由、采纳与结算均需可追溯；无动作不等于无 trace。
- 不改写旧冻结数据和历史评测结果。接口、参考和 scorer 的变化通过新版本发布，保留来源与证据指纹。

## 八、验收意图

1. 只读接口和 prompt 就能区分维护目标表与拆任务链；活动代码不再使用含糊的 `updates` 字段名。
2. 正常提案仍可经生产 Port、门面转换、review 和 harness 完整执行，原有目标表语义不变。
3. 冲突现场可以返回无任务的受阻意见，不触发解析重试，不产生虚构 task 或实际动作。
4. 可能完成只触发复核；judge 判定及 harness 的完成结算职责不迁移给规划器。
5. 合法修订后无 pending 有正常控制出口；进入 act 的前置条件仍被执行约束保护。
6. 连续受阻和复核未通过都有预算出口，正常失败、模型错误、无工作三者可在 trace 中区分。
7. FakeLLM 与 MockWorld 的集成用例验证新分支；真实调用原料对应的新评测参考能评价合理提案与合理受阻。
8. brain 仍无状态，跨模块转换仍在门面层；两侧数据方言与调用信封同步更新，不通过反向依赖共享实现。

## 九、本次不做与 spec 待定项

不统一两层的提案载荷；不修改 choose 的单步 Action，不给 choose 添加理由或停机权；
不增加目标表事实状态，不改记忆检索范围，不引入无限重规划或新的模型角色。

spec 必须落实：公共语义在各自方言中的形状、字段组合约束、表修订采纳的原子性、
无工作/受阻的图路由及跨层返回、复核预算、对应 trace/review 展示、结算与终止类别，
以及接口版本、旧数据读取和 checkpoint 指纹的影响。若需更新存档或采集，另列范围执行；
本 intent 不意味着立即重跑真实模型或二十场景采集。
